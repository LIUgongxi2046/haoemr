# Agent / DeepSeek 实际可用性审计

审计日期：2026-09-06。范围：当前工作区源码、本机 PostgreSQL `openemr2026_dev`（迁移到 V383）、8080 运行实例、用户提供测试密钥的 DeepSeek 官方接口。工作区基准 commit 为 `754fed9`，存在大量未提交变更；不能用该 commit 单独代表所审源码。本轮为执行与报告，没有修改业务代码、模型部署、临床审批或生产配置。

## 结论

**不是全部 agent 已真实可用，也不是纯静态 demo。准确定位是：有真实模型与业务工具执行能力的开发验证版本，混有仿真评测配置，并存在运行构建与源码不一致。尚无可信的全 agent 临床效果评分。**

当前注册 ACTIVE 的主 agent 14 个、子 agent 58 个。审计开始前，数据库记录了 9 次 `ModelGenerationCompleted / LIVE_MODEL`，覆盖 6 个主 agent、8 个子 agent。历史调用覆盖率分别为 42.9% 和 13.8%，这是“至少有一次成功调用记录”的覆盖率，不是效果准确率，更不代表当前全部功能可用。

## 当前可用性障碍

1. **当前源码找不到可路由的合格模型。** 数据库两个 ACTIVE/APPROVED/READY 模型均为 `test_only=true`；按当前源码完整选择条件，合格模型数为 0。`V383__model_deployment_test_only_gate.sql` 将 DeepSeek 标记为测试用途，`MedicalAgentHarnessService.java:934` 的选择逻辑要求 `test_only=false`。这是测试与临床运行的隔离门禁，不应为了验收直接改布尔值跳过发布流程。
2. **本机旧运行实例与源码不一致。** 8080 进程运行 `build/libs/openemr2026-0.1.0-SNAPSHOT.jar`；当前源码包名为 `org.haoemr`，旧构建使用旧版开发口令。最直接的行为证据：旧实例接受了绑定 `test_only=true` DeepSeek 的任务，而当前源码应拒绝。当前构建目录中已找不到该运行 JAR，无法给运行二进制补作哈希校验。需要重新生成可追溯构建再验收，不能将源码门禁判断当作已运行实例的实测拒绝结果。
3. **本次应用测试未跑通模型。** 无患者上下文的 `PRE_VISIT_SUMMARIZER` 任务在工具阶段报 `CONTEXT_NOT_PERMITTED`，最终主任务为 PARTIAL，`execution_mode=NOT_STARTED`。不把这一例视为所有患者场景均失败；它证明当前无患者路径仍存在限制，且表层状态不足以判成功。

应用测试先按当前源码公开开发口令登录返回 401，核对仓库旧构建配置后用旧版公开开发口令登录成功。没有尝试猜测用户密码或修改账号。仅新增一个无患者、零模型调用的审计任务及其上下文/事件记录，保留以便复核：`511399dc-8683-49fe-affd-a13251ae8172`。

## 哪些是真实实现，哪些仍不足

- 真实实现：HTTP 模型传输、从业务数据库读取授权文书/医嘱/结果等工具、运行队列与 worker、调用 token/耗时/事件台账、患者上下文边界、审批后进入业务流程的候选输出机制。历史 LIVE_MODEL 与工具调用记录证明并非只有页面展示。
- 当前编排偏固定流程：`AgentOrchestrator` 按页面/关键词选主 agent；harness 按已配置节点逐个调用子 agent。各子 agent 共用基础提示词和 `summary/facts/gaps/warnings` 输出解析。名称、动作、契约名称提供任务差异，但不是每个专科都有经过独立效果验证的专用模型或完整决策流程。
- Skill 依赖在该执行链中主要检查目录登记与 ACTIVE 状态；没有在模型请求中看到技能正文加载或专用 Skill 执行器。不能以“Skill 已登记”推断技能已完整执行。
- 子 agent 的主路径输出供医生审阅的候选，不直接代表已开药、已签署、已调度设备或已完成随访；这些需要下游领域操作与业务状态证据。

## 为什么页面高分不能采信

1. 数据库 ACTIVE `AGENT_EVAL` 中的业务分数约为 96.8%–99.0%，19 条业务配置带 `tertiary-hospital-simulation` 标记。`V315`、`V349` 等迁移直接填入 `measured_score` 和样本数；不是本轮实测所得。另有两个 E2E 配置的 0.97 来自表单填值。
2. `evals/deepseek/run-harness.mjs:33` 把无跨样本 ID 当作引用准确率，把无少数动作词当作临床事实性；第 40–41 行将超时恢复和取消恢复固定为 1。单条评测还把 `unauthorized_side_effect` 固定为 false。这些指标并没有测量其名称所表达的完整含义。
3. 本轮重跑组合检查 PASS，但它只校验旧版 5 主/33 子目录与静态安全案例，不能覆盖当前 14 主/58 子。
4. 原 DeepSeek harness 配置检查返回 `INTEGRATED_READY_NOT_EXECUTED`，原因是当前 shell 未配置其执行环境与 provisioned 门禁。本轮供应商探针为用户授权的合成测试，没有修改该配置或冒充院内治理批准。

## 评分与下一步

- 简单文书结构能力：本轮 20/20 通过，范围很窄。
- 全 agent 端到端可用性：证据不足，且当前源码和运行实例不一致，不能给“全部可用”结论。
- 专科临床效果：**未形成有效评分**。现有 96.8%–99.0% 不可作为医学效果承诺。
- 发布建议：维持开发/合成验证用途；就“全 agent 已验收”判断为 NO_GO。

优先完成：统一运行构建与源码 → 正式区分测试模型和可用模型发布状态 → 给 58 个子 agent 逐个建立合成场景的 UI/API/工具/模型/候选链证据 → 用有专家标准答案的分专科病例集验证事实、引用、危险遗漏与错误建议 → 实际执行超时、取消、越权和跨患者测试。应按具体场景通过情况放行，不以统一大分数替代。

## 证据文件

- `database-snapshot.json`：审计前目录、模型状态及历史成功调用，不含患者正文或密钥。
- `provider-results.json`：21 次直接 API 调用结果，含 request ID、usage 和合成输出。
- `provider-progress.jsonl`：直接供应商测试执行日志。
- `application-results.json`、`application-terminal.json`：本次应用任务受理与最终状态。
- `probe.mjs`、`application-probe.mjs`：可重复探针；密钥仅从用户指定文件读入内存。
- `manifest.json`：源码基准、工作区脏状态与数据集 SHA-256。
