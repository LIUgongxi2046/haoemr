# HaoEMR 单机安装与运行设计

日期：2026-09-28。状态：`PROPOSED`。能力类型：`DESIGN`。安装与运行验收：`NOT_RUN`。

依据：本次用户关于单机安装包的咨询、当前工作目录中的代码及部署配置。Git HEAD 为 `f36253f`，工作目录包含未提交修改，本文依据包含这些修改的文件内容。本文提供改造设计，未执行业务代码修改、安装、服务启动或数据复制。

## 1. 目标、范围与前提

交付一个安装程序，包含运行 HaoEMR 所需的应用、Java 运行环境、PostgreSQL 程序和经过审核的基础配置。用户安装完成后，通过桌面快捷方式进入现有界面，日常使用无需执行开发命令。

保留 Vue、Spring Boot、PostgreSQL、现有业务模块、权限与审计规则，以及原有菜单和设计风格。单台电脑支持多个授权账号分别登录，创建人与审批人的职责分离规则继续有效。

用户尚未指定操作系统。本文使用 Windows 的安装程序、系统服务和数据目录说明交付方式；macOS、Linux 使用各自的安装与服务管理机制，业务代码共用。每个操作系统及处理器架构需要独立构建、安装和验收。

单机部署要求业务服务和数据库在同一电脑运行；完全离线要求所有承诺可用的能力均不依赖外部网络。两项分别验收。AI、可信签署、OCR、文件扫描和医院接口应当逐项注明提供方式、依赖和实际可用状态。

性能要求按目标电脑、真实授权数据规模及模型配置测量。包体大小、最低内存、启动耗时、业务响应时间、可接受数据恢复时间和数据恢复时间点目前没有测量结果，不使用开发环境历史测试作为单机版承诺。

## 2. 现有工程与业务边界

| 对象 | 当前证据 | 单机交付要求 |
| --- | --- | --- |
| 前端 | `web/vite.config.ts` 配置开发服务及 API 代理；`deploy/web-synthetic.Dockerfile` 执行 `npm run dev` | 构建静态资源，由本机应用提供；用户电脑无需 Node.js 或 Vite |
| 后端 | `build.gradle.kts` 使用 Java 21、Spring Boot 4.1.0、JDBC、Flyway | 交付构建完成的应用和 Java 运行环境，具有独立服务生命周期 |
| 数据库 | 当前服务及迁移使用 PostgreSQL、JSONB 和数据库锁 | 安装专属 PostgreSQL 实例，保留业务查询、事务、约束和迁移规则 |
| 登录 | `DevelopmentSessionController` 和 `DevelopmentSessionService` 仅用于 `dev-synthetic` | 实现正式本地账号认证，建立独立会话、权限和恢复流程 |
| 其他运行配置 | `FailClosedClinicalIdentityProvider` 拒绝未配置正式身份的请求 | 新增 `standalone` 配置与身份提供者，明确 Bean 的启用条件 |
| 首次管理员 | `FirstAdministratorBootstrap` 已创建机构、用户、角色和审计；Runner 要求 `prod`、非 Web 进程及 OIDC issuer | 复用一次性创建与幂等规则，增加本地凭据建立和受控安装授权 |
| 签署 | `FailClosedClinicalSignatureProvider` 在非开发环境返回服务不可用 | 接入实际可信签署与验证服务；配置字段齐全不能代替签署成功 |
| 归档 | `FileSystemArchiveObjectStorage` 返回 `FILESYSTEM_DEV`，使用文件权限和保留标记 | 实现正式本地存储、权限、完整性与保留策略，验证 Windows 文件系统行为 |
| 数据目录 | `application.yml` 为附件和模型秘密配置了临时目录默认值 | 安装时指定持久目录，缺少目录或权限时直接报告错误 |
| 初始化数据 | 存在空库迁移测试、模块配置包及初始化检查 | 对当前完整迁移序列重新验收；安装后业务数据为空，初始配置来源明确 |
| 就绪检查 | `SystemReadinessController` 返回 `SystemReadiness.ready(version)` | 安装启动检查需要覆盖数据库、迁移、目录、认证及必要业务能力 |

系统外部参与方包括电脑管理员、应用管理员、临床操作人员，以及按配置接入的模型、签署和医院服务。电脑管理员拥有操作系统管理能力；应用审计与文件校验应当明确这一信任边界。

## 3. 架构决策

所有决策状态均为 `PROPOSED`，实施责任由后续开发任务指定。

| 决策 | 采用方式 | 依据与代价 | 验证要求 |
| --- | --- | --- | --- |
| ADR-01 应用交付 | 将 Vue 构建资源纳入 Spring Boot 制品，通过桌面启动器打开默认浏览器 | 保留现有路由与页面；需要修改构建顺序、静态资源访问规则及缓存版本管理 | 用户电脑不安装开发工具，页面、静态资源和 API 均能访问 |
| ADR-02 数据服务 | 安装专属 PostgreSQL，监听本机地址，使用独立服务名称、数据库与账号 | 复用当前数据能力；发行方负责数据库补丁、版本兼容和生命周期管理 | 与电脑已有 PostgreSQL 共存；重复安装不覆盖已有数据 |
| ADR-03 身份与配置 | 增加 `standalone` 正式运行配置，复用现有人员和角色模型 | 需要本地认证、首次凭据设置、会话撤销与管理员恢复；不能启用开发身份 | 未登录、账户停用、权限撤销、跨角色访问分别正确拒绝 |
| ADR-04 安装程序 | Java 应用使用 `jpackage` 生成平台应用镜像；安装编排负责数据库、系统服务、目录权限、快捷方式及卸载 | `jpackage` 提供应用与运行环境封装；数据库初始化及应用服务注册需要明确实现和验证 | 每个目标平台从没有开发环境的电脑完成安装 |
| ADR-05 外部能力 | 每项能力使用明确的真实提供者和配置状态 | 完全离线的 AI 需要本机模型与推理服务；签署需要实际签署和验证机制 | 缺少依赖时在对应操作位置报告原因，禁止自动替换模型或生成成功结果 |

`jpackage` 支持 Windows `exe/msi`、macOS `pkg/dmg`、Linux `deb/rpm`，能够携带 Java 运行环境，并要求在目标平台构建对应安装包。[Java 21 官方打包说明](https://docs.oracle.com/en/java/javase/21/jpackage/packaging-overview.html)

PostgreSQL 的 `pg_ctl register` 支持在 Windows 注册专属数据库服务。[PostgreSQL 18 服务管理说明](https://www.postgresql.org/docs/18/app-pg-ctl.html)

| Spring Boot | 提供 Vue 静态资源、认证、业务 API、现有后台任务 | 业务记录、审计事件、任务状态 | 单实例运行，继续执行现有权限校验 |
| PostgreSQL | 保存业务、配置、账号、审计及任务状态 | 事务读取与写入结果 | 专属数据库账号；安装迁移权限与日常运行权限分别配置 |

| 现有 AI 执行服务 | 接收已授权任务，调用实际配置的模型和工具 | 任务结果、引用、人工确认及审计 | 复用现有执行边界；本次安装设计不新增 Agent 调度系统 |

程序文件与可变数据分别管理。Windows 可采用 `C:\Program Files\HaoEMR` 保存程序，`C:\ProgramData\HaoEMR` 保存配置、数据库、附件和日志。备份目标单独配置，可以选择另一磁盘或受控外部介质。

系统管理继续承载配置：组织机构与账号沿用原页面，模块安装沿用参数开关，安装及运行记录沿用通知任务，审计沿用管理审计。运行状态、备份恢复和应用版本增加为现有页面的功能区域，不增加主菜单。

## 5. 安装、启动与业务运行流程

1. 安装程序校验制品来源、文件摘要、平台、可写目录和所需空间，检测已有实例。失败立即停止，展示具体原因。
2. 安装应用与运行环境，建立专属数据库实例，生成独立凭据，设置仅本机访问及目录权限。已有实例必须进入升级路径。
3. 在独立安装步骤执行数据库迁移。迁移未完成时不启动正常业务服务；保存当前步骤和可恢复状态。
4. 使用仅安装过程持有、短期有效且只能使用一次的授权建立机构和首个管理员。入口限定本机；并发请求不能重复创建，重复执行不能重置管理员。
5. 管理员设置本地密码及恢复凭据，进入现有组织与人员页面完成配置。安装过程不创建患者、就诊、医嘱、固定测试账号或自动模型结果。
6. 从经过认可的配置包建立模板及规则，沿用原发布和独立审批流程，记录来源、版本与实际生效状态。
7. 启动器等待数据库、结构版本、身份认证及必要目录可用后打开登录页。重复打开复用同一实例；端口冲突时报告占用，不终止其他程序。
8. 每次业务请求执行账号、角色、机构及患者范围检查。权限拒绝直接返回错误；需要人工确认的操作停留在原确认步骤；所有依赖满足后才能提交业务结果。
9. AI 任务继续使用原有持久状态和人工采用流程。网络中断、模型不可用、超时、用户取消各有明确终态；进程重新启动后根据持久任务记录核对状态，不重复执行已经完成的写入。
10. 关闭浏览器保留后台服务运行，以支持既有定时任务。明确执行停止服务时，应用停止接收新任务并完成受控退出，随后停止数据库。

首次配置与日常业务使用不同授权范围。未初始化时只允许经过安装授权的设置动作；不能通过匿名开启管理 API 完成安装。

## 6. 数据、会话、缓存与外部服务

- 浏览器与本机应用同源访问。静态资源按发布版本缓存；会话、患者上下文及业务查询仍按用户、角色、机构和就诊隔离，退出登录清除会话相关缓存。
- 本地认证复用当前密码散列、锁定和会话撤销机制中经过验证的逻辑，并建立正式提供者。修改密码、停用账号、撤销角色后验证已建立会话的实际权限。
- 对环回地址服务检查 Host、Origin、认证和请求保护规则；确定本机 HTTPS 证书的安装、信任及更新方式，配置只影响本应用。
- 应用版本、数据库结构版本、配置包版本和模型配置版本分别登记。安装清单由安装程序产生，启动、升级和恢复过程读取；出现版本不匹配时拒绝继续业务运行。
- 数据库、附件、应用配置和可恢复的必要秘密共同构成可恢复实例。操作系统绑定的秘密需要受保护的迁移机制，单独复制文件不能视为跨电脑恢复成功。
- AI 支持连接实际外部服务，或者接入本机真实推理服务。模型制品、许可、上下文长度、内存与处理器需求需独立验证。基础病历保存、查询和权限管理不依赖模型可用性。
- 签署、OCR、归档校验、文件扫描、医院接口分别配置和验证。正式签署以及依赖签署的归档流程，在真实提供者尚未完成接入时继续列为未完成能力。
- 日志按大小与保留周期管理，不记录密码、令牌和完整临床正文。业务记录、审计证据与可清理日志使用不同保留规则。

## 7. 升级、备份与逐功能验收

升级包声明支持的起始应用版本、数据库结构范围及 PostgreSQL 主要版本。应用升级和数据库主要版本升级分别管理。升级前验证目标制品、可用空间、活动任务及备份结果；随后执行受控停止、迁移、启动与业务检查。失败时禁止启动不兼容的程序版本，也不删除现有数据。

备份需要覆盖数据库、附件、配置和必要秘密。为了得到一致的恢复点，在受控维护窗口暂停业务写入与后台写任务，记录实例及版本，使用 PostgreSQL 备份工具保存数据库并保存对应附件与配置。恢复应当写入独立目标目录和数据库，完成校验后再由管理员选择启用。若涉及恢复到旧时间点，必须显示所选恢复点之后的数据影响。

数据库备份支持多种方式，具体选择需要结合恢复目标制定；附件和秘密的恢复验证由应用负责。[PostgreSQL 18 备份说明](https://www.postgresql.org/docs/18/backup.html)

卸载程序停止并移除本应用服务，默认保留业务数据与备份，明确显示保留位置。电脑关闭期间无法产生新的本机定时备份，重新启动后需要提示缺失备份并按既定规则补做。

## 8. 安全控制与发布条件

数据库和应用默认只监听本机地址，安装程序不创建公共网络开放规则。数据库采用专属非超级用户运行账号和独立密码，服务目录仅允许授权账号访问。

安装程序、升级包及配置包校验来源与完整性，禁止安装目录中的任意文件自动执行。秘密使用操作系统保护机制，备份使用独立加密和访问控制。源码、依赖清单、许可证及发行版本信息随交付过程管理。

程序以受限身份运行；临床业务仍执行原角色和数据范围检查。单机模式不取消创建人与审批人的分离要求。安全审计记录和签署证据分别验证，文件只读属性不能独立证明可信归档能力。

发布检查分别确认应用安装可用、临床业务完成、外部服务真实接入以及数据恢复可用。正式签署、归档、真实账号和数据恢复仍有未通过项目时，不声明完整临床单机版已经交付。

本次设计依据代码检查和官方文档，没有执行新安装包构建、运行或验收。后续实施应当以届时的当前文件和目标平台配置建立新的验证记录。
