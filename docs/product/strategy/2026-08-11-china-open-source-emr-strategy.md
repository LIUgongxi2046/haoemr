# 中国医疗机构首选开源 EMR：战略方案

> 版本：v0.2  
> 更新日期：2026-08-11（Asia/Shanghai）  
> 方案状态：`CREATED`  
> 决策模式：S001 / `DECIDE`  
> 当前建议：`INVEST`——投入产品定义、自研临床内核和开源发行能力；在通过安全与临床门禁前，不声明可直接用于生产诊疗。

## 一、v0.2 战略修订

本版依据项目发起人的明确意见完成四项根本调整：

1. `EXPLICIT`：不把产品限定为诊所系统。长期目标覆盖诊所、基层医疗机构、一级、二级和三级医院。
2. `EXPLICIT`：不基于 OpenEMR、OpenMRS、Medplum、Bahmni、OpenHIS 等现有开源医疗系统二次开发；它们只作为竞品、需求和工程经验参考。
3. `EXPLICIT`：首要目的不是商业收入，而是做出国内最好的开源 EMR，并沉淀医疗信息化、产品、架构、工程和开源治理能力。
4. `EXPLICIT`：GitHub Stars 和有效下载量是一级结果指标；机构用户活跃、商业转化等属于后续指标。

与 v0.1 相比，已删除“只面向中医/中西医连锁诊所”“Medplum 长期底座”“双底座 PoC”“付费试点作为核心门禁”等结论。

## 二、执行摘要

### 2.1 一句话战略命题

> 从零自研一套中国原生、面向各级医疗机构、模块化、可私有化部署、临床可信、接口开放的开源 EMR；让诊所能够独立使用，让二三级医院能够按模块部署或与既有 HIS、LIS、PACS 等系统集成，并通过优秀代码、文档、演示和发布体验形成国内最有影响力的医疗开源项目。

- 来源：`EXPLICIT` + `INFERRED`
- 置信度：高
- 反证：如果从零自研无法在合理周期内形成可运行的通用临床内核，或公开发布后持续没有下载、独立部署和开发者反馈，则需要缩减模块范围，但不自动转向现有开源 EMR 底座。

### 2.2 核心战略判断

1. **目标用户广，产品内核统一。** 不按诊所版、医院版复制多套代码；用同一临床内核、模块组合和部署画像服务不同规模机构。
2. **能力边界分阶段，机构边界不预先封死。** 第一阶段先完成所有机构共用的临床内核与门诊参考应用，同时在模型中支持组织、科室、病区、床位和住院就诊；随后补齐住院与医院级能力。
3. **自研的是医疗业务系统，不是重新发明所有基础软件。** 可以使用 PostgreSQL、缓存、消息队列、前端框架、容器和通用安全库，但不能以其他开源 EMR/HIS/EHR 的代码或数据模型作为产品底座。
4. **开源产品力优先。** 代码质量、架构清晰、安装成功率、演示体验、中文与英文文档、版本节奏、Issue 响应和社区治理都是产品的一部分。
5. **Stars 与下载量是一级指标。** Stars 表示传播与关注，稳定版本有效下载表示使用意愿；两者都要保留原始数据，不能只做一个不透明的综合分数。
6. **医疗安全仍是发布底线。** GitHub 增长不能替代病历版本、签名、审计、权限、备份恢复和数据一致性门禁。

## 三、目标用户与产品使用方式

### 3.1 目标机构

| 机构类型 | 产品使用方式 | 重点能力 | 战略状态 |
|---|---|---|---|
| 诊所、门诊部、基层医疗机构 | 可独立部署并启用预约、接诊、病历、医嘱/处方、收费及基础运营模块 | 简单安装、低运维、完整门诊闭环 | `PLANNED` |
| 一级医院 | 独立部署或连接现有收费、药房、检验和影像系统 | 多科室、权限、门诊与基础住院 | `PLANNED` |
| 二级医院 | 作为院级 EMR 或临床工作台，与既有 HIS/LIS/PACS 集成 | 住院病历、医嘱、护理、质控、接口、审计 | `PLANNED` |
| 三级医院 | 以模块、专科、科研或替换路径逐步接入，不要求一次性替换全院系统 | 高并发、复杂组织、专科扩展、数据平台、互操作 | `PLANNED` |
| 医疗信息化开发者与实施商 | 二次开发、部署、适配和贡献代码 | API、SDK、文档、扩展点、升级兼容 | `PLANNED` |

这里的“覆盖”是产品战略边界，不表示 v1.0 已经满足所有等级医院的全部功能和评审要求。二三级医院从第一天就是目标用户，但能力按可验证模块逐步交付。

### 3.2 关键用户

- 医生：门急诊和住院病历、诊断、医嘱、处方、签署、患者时间线。
- 护士：执行、护理记录、生命体征、交接班和病区工作台。
- 药师：处方审核、调剂、发药、用药记录和药品基础数据。
- 医技人员：检验、检查申请与结果回传；初期以集成为主。
- 病案与质控人员：病历归档、缺陷检查、封存、复制、编码和质量追踪。
- 医疗管理者：组织、科室、人员、权限、数据质量和审计。
- IT 与实施人员：安装、配置、迁移、集成、升级、备份恢复和故障处理。
- 开源开发者：阅读架构、运行示例、开发插件、修复 Issue 和贡献 PR。

### 3.3 通用临床主链

```text
机构/科室/人员与权限
        ↓
患者主索引与身份核验
        ↓
门诊、急诊或住院就诊
        ↓
病历文书与结构化临床数据
        ↓
诊断、医嘱、处方、执行与结果
        ↓
签名、归档、质控、版本与审计
        ↓
交换、导出、备份、恢复和长期保存
```

诊所可以在这条主链旁启用收费、药房和库存；医院可以通过接口连接原有系统。收费与 ERP 不应反向绑死临床内核。

## 四、问题、价值与替代方案

### 4.1 要解决的问题

| 对象 | 当前常见问题 | 产品价值 |
|---|---|---|
| 医务人员 | 界面复杂、重复录入、临床信息分散、病历质控滞后 | 更清晰的临床工作台和可配置文书流程 |
| 医疗机构 | 系统封闭、接口成本高、数据迁移困难、升级依赖厂商 | 代码和数据自主、标准接口、可审计升级与迁移 |
| IT/实施团队 | 遗留架构、文档不足、环境难复现、现场分叉严重 | 清晰模块边界、自动化安装、公开文档和扩展机制 |
| 开发者 | 缺少现代、可运行、面向中国流程的开源 EMR 项目 | 可学习、可部署、可贡献的真实医疗软件工程样板 |
| 患者与监管 | 病历访问、修改、签署、封存和长期保存难以验证 | 完整证据链、权限、审计和可验证导出 |

### 4.2 现有替代方案

1. 商业 HIS/EMR：功能和实施经验较完整，但代码、接口、迁移与长期自主权取决于供应商。
2. 现有国际开源 EMR：有真实积累，但业务、技术栈、许可和中国适配不符合本项目的自研目标。
3. 国内源码项目：部分流程贴近，但工程质量、安全、许可、文档和社区持续性不稳定。
4. 医院自研或项目制外包：可定制，但容易形成单院版本、技术债和高维护成本。

现有开源项目仍有研究价值，但不能被复制为本项目的业务内核。允许参考公开标准、法规、交互模式和通用工程实践；禁止复制其受版权保护的代码、界面资产、私有数据模型或带不兼容许可证的实现。

## 五、市场与开源竞品基准

### 5.1 医疗机构范围事实

国家卫健委《2024 年我国卫生健康事业发展统计公报》显示，截至 2024 年末，全国有医院 38,710 家，其中公立医院 11,754 家、民营医院 26,956 家；另有诊所、医务室和护理站 351,736 家。该数据说明目标使用场景横跨不同规模医疗机构，但不能直接推导本项目的下载量或商业市场规模。

- 状态：`OBSERVED`
- 核查日期：2026-08-11
- 置信度：高

### 5.2 GitHub 竞品基准

| 项目 | 2026-08-11 GitHub 快照 | 对本项目的意义 |
|---|---:|---|
| OpenEMR | 约 5.4k Stars | 长期影响力标杆；功能与历史积累不能直接等同产品质量 |
| Medplum | 约 2.6k Stars | 现代开发者平台与文档、发行体验参考 |
| OpenMRS Core | 约 1.9k Stars | 医疗社区和长期治理参考 |
| Bahmni Core | 约 166 Stars | 说明真实部署价值与单仓库 Stars 并不总一致 |

Stars 会随时间变化，且多仓库项目之间不完全可比。战略上仍采用 Stars 和下载量作为一级指标，但必须固定统计口径并每季度更新竞品快照。

### 5.3 长期竞争目标

- 国内目标：成为中文语境中认知度最高、安装体验最好、文档最完整的开源 EMR。
- 国际目标：GitHub 影响力进入开源 EMR/EHR 核心项目第一梯队。
- 量化终局：主仓库 Stars 超过届时主要开源 EMR 主仓库基准，稳定版本下载持续增长，并出现无需核心作者参与的独立部署和外部贡献。

## 六、产品战略与自研边界

### 6.1 自研原则

必须自主设计和实现：

- 医疗机构、科室、病区、人员和角色权限模型。
- 患者主索引、身份合并与拆分。
- 门诊、急诊、住院就诊模型。
- 病历文书、结构化数据、模板与版本管理。
- 诊断、医嘱、处方、执行、结果和临床时间线。
- 签名、归档、封存、质控、访问审计和证据导出。
- 插件体系、业务 API、迁移协议和中国适配层。

可以使用成熟通用组件：

- 数据库、缓存、对象存储、搜索、消息队列和容器平台。
- Web/移动端框架、通用身份协议、密码学库和可观测性组件。
- HL7、FHIR、DICOM、ICD 等公开标准及合法获得的术语资源。

“从零自研”不等于自创密码学、数据库或医疗标准，而是对临床业务模型、产品体验、代码主权和演进路线负责。

### 6.2 单内核、分层能力

| 层级 | 内容 | 目标 |
|---|---|---|
| L0 临床内核 | 组织、人员、权限、患者、就诊、文书、医嘱、版本、审计 | 所有机构共享，不允许按客户分叉 |
| L1 门诊参考应用 | 预约、挂号、接诊、处方、结果、签署、复诊时间线 | 诊所可独立使用，医院门诊可集成使用 |
| L2 住院基础 | 入院、病区床位、住院病历、医嘱执行、护理、出院 | 支撑一级和二级医院基本场景 |
| L3 医院增强 | 高级质控、专科模板、复杂权限、高可用与数据交换 | 面向二级、三级医院渐进增强 |
| L4 生态扩展 | 插件、连接器、SDK、示例与开发者工具 | 形成开源传播和二次开发能力 |

### 6.3 非目标

前 180 天不承诺：

1. 一次性交付三级医院全部临床、医技、管理和评审功能。
2. 重做成熟的 LIS、PACS、ERP、医保核心、CA 或支付系统；优先定义集成契约。
3. 同时完成所有专科深度模板。
4. 用 AI 自动作出诊断、处方或替代医务人员签名。
5. 为单一机构建立无法回归主线的长期代码分叉。
6. 为追求 Stars 发布无法安装、缺少测试或存在已知高危漏洞的版本。
7. 将 “OpenEMR” 用作本项目正式产品名；当前统一使用 “HaoEMR”，避免与现有 OpenEMR 项目混淆。

这些是交付顺序限制，不是目标机构限制。

## 七、核心差异化与能力沉淀

### 7.1 产品差异化

1. **中国原生**：从法规、病历书写、组织权限和本地集成需求出发，而不是在国外系统上覆盖中文界面。
2. **现代且可理解**：清晰的模块边界、类型契约、迁移机制和测试体系，让开发者真正能读懂和贡献。
3. **全层级可演进**：同一内核服务诊所和医院，避免“小诊所玩具”与“医院巨石系统”二选一。
4. **临床可信**：版本追加、签名、归档、封存、审计、长期保存和恢复证据从第一天进入内核。
5. **真正可开源使用**：演示数据、一键安装、升级文档、API 示例、中文/英文文档与安全披露流程完整。

### 7.2 要沉淀的能力

- 中国 EMR 业务与法规知识体系。
- 通用临床数据模型和工作流抽象能力。
- 医疗安全、隐私、审计和长期数据治理能力。
- 复杂 B 端产品、模块化系统和可扩展架构能力。
- 自动化测试、交付、升级和可观测性能力。
- 开源品牌、社区治理、技术写作和开发者运营能力。

## 八、开源策略与商业模式位置

### 8.1 开源优先

建议主仓库从具备最小可运行骨架后公开开发，并具备：

- 清晰 README、产品截图/演示视频、路线图和架构说明。
- 五分钟体验路径和不超过三十分钟的本地启动路径。
- 脱敏/合成演示数据，不发布任何真实病历。
- CONTRIBUTING、CODE_OF_CONDUCT、SECURITY、版本支持和兼容政策。
- Good First Issue、讨论区、RFC 流程、Issue 模板和公开里程碑。
- 中文为主、英文同步的核心文档，扩大国内外开发者可发现性。
- 稳定的 Release、容器镜像、校验值、变更日志和升级说明。

项目已选择 `AGPL-3.0-only` 作为社区版许可证，并保留独立商业授权路径，以限制未经回馈的闭源网络服务改造；贡献采用 CLA + DCO。商标、CLA 文本和第三方依赖/医学知识资产仍需在首次接收外部代码或公开发行前完成法律与许可证复核。

### 8.2 商业模式是远期选项，不是前置门禁

项目可以长期保持非商业化。若未来需要形成可持续投入，可选择：

- 托管与专属部署。
- 企业级支持、升级和 SLA。
- 数据迁移、接口适配和实施服务。
- 培训、认证与生态合作。
- 合规、安全和高可用发行支持。

前 180 天不以收入、付费转化、CAC 或 LTV 作为继续/停止条件。只记录潜在成本：开发时间、基础设施、发布、文档、安全测试、社区维护和真实试点支持。

未来单位经济性参考公式保留为：

```text
月度可持续贡献
= 托管/支持/实施等收入
- 基础设施、第三方服务、安全与运维成本
- 实施、迁移、支持和社区维护工时成本
```

## 九、一级指标与质量护栏

### 9.1 一级北极星指标组

1. **GitHub Stars**
   - 累计 Stars。
   - 30 天净新增 Stars。
   - Star 增长来源：发布、文章、演示、社区推荐或其他渠道。
2. **有效下载量**
   - GitHub 稳定版本资产下载量。
   - 容器镜像拉取量，但需要剔除 CI、重复构建和机器人噪声。
   - 安装器或部署包下载量。
   - 能够回传匿名成功事件时，单独统计成功启动量；默认关闭遥测并明确告知。

Stars 是传播与认可的领先指标，下载是使用意愿指标。两者均高于机构活跃、商业收入和销售线索等运营指标。

### 9.2 180 天建议目标

以下是 `PLANNED` 的挑战目标，不是已验证预测；公开发布 30 天后应按真实基线修订：

| 指标 | Day 90 | Day 180 |
|---|---:|---:|
| GitHub Stars | 300 | 1,500 |
| 稳定版本有效累计下载 | 100 | 1,000 |
| 外部独立成功安装 | 5 | 20 |
| 外部 Issue/Discussion 作者 | 10 | 50 |
| 外部代码或文档贡献者 | 3 | 10 |

长期目标是超过届时主要开源 EMR 主仓库的 Stars 基准；按 2026-08-11 快照，OpenEMR 约为 5.4k Stars。该数字需季度更新，不能当作永久静态目标。

### 9.3 不可牺牲的质量护栏

| 护栏 | 最低要求 |
|---|---|
| 安装 | 新用户按文档可在干净环境运行演示系统 |
| 测试 | 核心数据一致性、权限、审计和迁移测试必须自动化 |
| 安全 | 无已知未处置高危漏洞；提供私密漏洞报告通道 |
| 数据 | 默认只含合成数据；真实数据进入需单独授权和安全门禁 |
| 恢复 | 备份必须经过恢复演练并校验病历、附件和审计一致性 |
| 发布 | 版本可追溯、含校验值、变更日志、升级与回滚说明 |

用户活跃、医生周活、机构留存、商业收入和销售转化列为二级运营指标，待出现真实机构用户后再建立基线。

## 十、护城河假设

| 护城河 | 形成机制 | 当前状态 | 反证 |
|---|---|---|---|
| 自主临床内核 | 关键业务模型与代码完全自主、持续演进 | `PLANNED` | 长期仍依赖大量复制或不可控外部系统 |
| 中国医疗知识体系 | 法规、病历、质控、组织和接口知识进入产品与文档 | `PLANNED` | 只停留在通用 CRUD，无法支持真实流程 |
| 工程与文档体验 | 一键运行、升级、测试、API、示例和中英文文档 | `PLANNED` | 下载多但无法安装，Issue 长期无人响应 |
| 社区品牌 | 稳定发布、透明路线图、快速反馈和外部贡献 | `PLANNED` | Stars 来自一次性传播，下载和贡献不增长 |
| 全层级扩展能力 | 同一内核逐步支持诊所、门诊和住院 | `PLANNED` | 每进入一种机构就必须复制或推翻核心模型 |

## 十一、五个优先实验

| # | 假设 | 方法与样本 | 周期 | 成功阈值 | 停止/调整条件 |
|---|---|---|---|---|---|
| E1 跨机构通用性 | 同一临床内核可覆盖诊所和医院的共同概念 | 访谈/评审至少 3 家诊所或基层机构、2 家二级医院、2 家三级医院；覆盖医生、护士、病案、IT | 2–3 周 | 组织、患者、就诊、文书、医嘱、签名和审计的公共模型得到多数评审者认可；差异可通过模块或配置处理 | 关键概念必须按机构复制模型，则暂停编码并重做领域边界 |
| E2 自研垂直切片 | 不依赖现有开源 EMR 底座也能实现可信临床主链 | 自研组织/权限、患者、就诊、病历、签名版本和审计的端到端切片 | 4–6 周 | 仿真患者可完成门诊和住院两类就诊记录；版本和审计可验证；依赖清单无其他 EMR 代码 | 切片无法稳定演进或核心模型反复推翻，则缩小功能但保持自主内核 |

## 十二、90 天路线

### Day 1–14：产品宪章与开源骨架

- 明确产品正式名称候选、品牌边界、许可证候选和贡献方式。
- 形成诊所、医院门诊和住院三类场景地图及共同领域词汇表。
- 建立公开仓库骨架、README、路线图、治理、安全和贡献文档。
- 形成 S002 PRD 输入和 E1 跨机构评审材料。

退出门禁：不再使用“只面向诊所”的范围定义；公共临床内核边界完成评审；没有引入现有开源 EMR 代码。

### Day 15–45：自主临床内核垂直切片

- 完成 E2：组织/科室/权限、患者、就诊、病历文书、签名版本与审计。
- 同一仿真患者分别创建门诊和住院就诊，验证模型可扩展性。
- 建立数据库迁移、自动化测试、合成数据和安全扫描基线。

退出门禁：端到端切片可运行；核心数据与审计测试通过；第三方依赖许可证清单可审计。

### Day 46–75：参考应用与开发者体验

- 构建门诊参考应用和住院基础流程演示。
- 提供安装器/容器、API 示例、截图、演示视频和中英文文档。
- 完成 E3 外部开发者测试，修复全部启动阻塞。

退出门禁：未参与开发者可独立启动和修改；干净环境安装、升级、备份恢复可重复。

### Day 76–90：公开 Alpha

- 发布首个可下载 Alpha、容器镜像、变更日志和路线图。
- 发布架构文章、产品演示和贡献任务。
- 建立 Stars、Release 下载、容器拉取和外部安装的统计口径。

退出门禁：Release 可安装；无已知未处置高危漏洞；形成公开反馈闭环。Day 90 数字目标作为挑战值，不因未达到而牺牲质量。

## 十三、180 天战略门禁

| 阶段 | 时间 | 目标 | 必须交付 | 继续门禁 |
|---|---|---|---|---|
| G0 产品宪章 | Day 1–14 | 统一全层级目标和自研边界 | 产品宪章、场景地图、领域词汇、开源治理骨架 | 无诊所限定；无现有 EMR 底座依赖 |
| G1 自主内核 | Day 15–45 | 证明核心临床主链可以自研 | 组织、患者、就诊、文书、签名、版本、审计垂直切片 | 门诊/住院两类就诊可运行；核心测试通过 |
| G2 公开 Alpha | Day 46–90 | 证明项目可安装、可理解、可传播 | 参考应用、安装器、演示、API、中英文文档、首个 Release | 外部开发者安装成功；安全和恢复门禁通过 |
| G3 社区 Beta | Day 91–120 | 用真实开源反馈改善产品 | Issue/RFC 流程、插件示例、升级机制、第二轮 Release | 下载和独立安装持续增长；关键 Issue 有响应与版本闭环 |
| G4 医疗场景验证 | Day 121–150 | 证明诊所与医院都能使用同一内核 | 诊所独立部署演示、医院门诊集成、基础住院演示 | 不因机构类型分叉内核；P0 数据/权限缺陷为 0 |
| G5 稳定候选版 | Day 151–180 | 形成国内有影响力的开源 EMR 候选产品 | Release Candidate、升级/回滚、备份恢复、安全报告、治理文档 | 挑战目标 1,500 Stars、1,000 有效下载、20 次独立安装；质量护栏全部通过 |

Day 180 的决策：

- Stars、下载、独立安装和贡献均持续增长，且质量门禁通过：继续 `INVEST`。
- Stars 高但下载和安装低：产品展示成功、实际可用性不足，保持开源方向并优先修复安装与功能。
- 下载存在但跨机构模型失败：缩小当期模块，重构内核，不退回现有开源 EMR 底座。
- 所有开源信号长期接近零：`PIVOT` 产品定位、名称、文档、演示和传播策略，再进行一次有时限的发布实验。

## 十四、风险、依赖与机会成本

### 14.1 主要风险

1. **目标广导致范围失控。** 解决方式是同一内核分层交付，而不是排除二三级医院。
2. **从零自研周期过长。** 先做贯穿数据、权限、版本和审计的垂直切片，不先堆功能页面。
3. **Stars 变成虚荣指标。** 保留一级地位，但必须同时观察有效下载、独立安装和外部贡献。
4. **医疗软件被误用于生产。** Alpha/Beta 明确非生产用途；稳定版前完成安全、数据一致性和恢复门禁。
5. **许可证或代码来源污染。** 建立 SBOM、依赖审查和贡献来源声明；不复制现有 EMR 代码。
6. **医院需求把项目拖成全院 HIS。** EMR 专注临床记录与工作流，通过接口连接其他系统。
7. **真实病历泄露。** 仓库、测试、演示和 Issue 中只允许合成或严格脱敏数据。
8. **单人项目无法持续。** 需要文档化决策、自动化测试、公开路线图和低门槛贡献任务。

### 14.2 关键依赖

- 能参与评审的诊所、二级医院和三级医院临床/病案/IT 人员。
- 医疗数据、法规、病历质控和医院信息化专家。
- 具备产品、前端、后端、数据、安全、测试、DevOps 和文档能力的团队；当前团队配置为 `UNKNOWN`。
- 开源许可证、商标和医疗数据合规法律意见。
- 可公开使用的合成数据、标准术语测试集和接口模拟器。

### 14.3 机会成本

选择自研意味着放弃基于既有开源 EMR 快速获得大量现成功能，换取代码主权、现代工程能力、中国业务适配和长期学习沉淀。前 180 天必须优先做通用临床内核、工程质量和开源体验，暂缓全专科、全医技、复杂医保和大规模 AI 功能。

## 十六、交接给 S002 PRD

### 已确定输入

- 产品定位：面向诊所、基层、一级、二级和三级医院的中国开源 EMR。
- 核心目标：从零自研、能力沉淀、开源影响力和实际可下载使用。
- 一级指标：GitHub Stars、稳定版本有效下载。
- 产品原则：单一临床内核、模块化能力、诊所可独立、医院可集成。
- 首期产品范围：组织/科室/权限、MPI、门急诊/住院就诊、病历文书、诊断、医嘱、处方、签名、版本、审计、交换接口、备份恢复。
- 参考应用：门诊完整参考流程 + 基础住院流程演示。
- 非目标：180 天内完成三级医院全院级所有模块；以其他开源 EMR 为底座；用 AI 替代临床决策。
- 决策状态：`INVEST`，但生产医疗用途受安全和临床门禁约束。

### PRD 必须保留的 `UNKNOWN`

- HaoEMR 商标注册与长期持有主体。
- 技术栈、部署拓扑和详细架构，由 S004 决定。
- CLA、商标政策及第三方依赖/医学知识资产的最终法律复核。
- 180 天团队规模与可承诺产能。
- 门诊参考应用和住院基础流程的具体功能深度。
- 首批外部评审医院与可公开演示范围。
- 下载去重、容器拉取和匿名启动统计的最终口径。
