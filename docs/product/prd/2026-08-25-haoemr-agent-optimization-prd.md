## 0. 文档控制

### 0.1 目的

本 PRD 将主 PRD 中的平台级 AI 能力，收敛为可直接进入原型、架构、研发和验收的 Agent 优化版本。重点不是增加一个万能聊天框，而是把医疗工作拆成职责窄、可引用、可评测、可停用的 Agent；把可复用医疗流程固化为 Skill；把查询、校验和候选动作固化为最小权限 Tool。

本文定义产品行为、角色责任、状态、异常和验收口径，不替代 Agent LLD、API Schema、数据模型或部署设计。

## 2. 执行摘要

### 2.1 产品问题

当前产品虽然具备 AI 助手入口、Agent/Skill/Tool 名录和治理骨架，但用户面对的仍是功能名称，缺少稳定的任务契约：谁在什么上下文触发哪个 Agent、Agent 可调用哪些 Skill/Tool、结果如何引用、何时必须停下、如何确认或拒绝、失败怎样回到人工流程。若直接扩充通用 Agent，容易出现边界重叠、权限不可解释、输出不可验收和“目录已注册但能力不可运行”的问题。

### 2.2 产品命题

以“一个前台医助入口 + 多个主 Agent + 诊疗环节子 Agent + 版本化 Skill + 最小权限 Tool + 独立验证与人工确认”为核心形态：

1. 前台统一承接意图和上下文，但不拥有无限能力。
2. 主 Agent 对一个端到端用户任务负责，并根据当前诊疗阶段编排白名单子 Agent。
3. 子 Agent 对一个可独立失败、恢复和评测的诊疗环节负责，不直接扩展主 Agent 权限。
4. Skill 固化医疗工作流、模板、规则、Schema、失败语义和 Evals；没有独立目标和运行状态的能力不得仅为“显得智能”而注册成子 Agent。
5. Tool 只提供确定性、强 Schema、可审计的能力；任何副作用均进入候选或原业务审批状态机。
6. 临床用户看到来源、不确定项、变化差异和明确动作，再决定接受、修改、拒绝或接管。

### 2.3 目标

| ID | 目标 | 成功判据 |
|---|---|---|
| G-001 | 形成可落地的首批医疗 Agent 组合 | 5 个 P0 主 Agent 和 33 个候选诊疗环节子 Agent 均有角色、触发、输入、输出、边界、Skill/Tool 依赖、状态与 AC，并在 R0 决定哪些子 Agent 应下沉为 Skill。 |
| G-002 | 让 AI 结果可复核而非只“看起来合理” | 临床事实性陈述可回到来源；无证据项明确标识。 |
| G-003 | 让 Agent 权限和副作用可控 | 未授权 Tool 调用、跨患者引用和未批准副作用均被阻止并审计。 |
| G-004 | 让能力可持续演进 | Agent/Skill/Tool 版本锁定、评估、灰度、回滚和紧急停用形成闭环。 |
| G-005 | 证明真实工作流价值 | 通过影子和小规模灰度获得净复核时间、质量、采用和安全基线。 |

### 2.4 非目标

- 不建设自主诊断、自动处方、自动签署、自动给药/治疗或自动解除临床安全阻断。
- 不把模型自述、通用基准或演示成功当作临床有效性证明。
- 不允许 Agent 使用通用 SQL、通用 HTTP、任意代码执行或无患者范围的搜索 Tool。
- 不在首版建设无界多 Agent 社会、长期跨患者记忆或自我创建 Skill/Tool。
- 不在首版向患者开放急症症状分诊或未经批准的个体化治疗建议。
- 不在本 PRD 中承诺具体节时、采纳率或诊疗质量提升数值；这些目标须基于本地基线批准。

## 3. 用户、角色与责任

| 角色 | 核心任务 | 可做 | 不可做 |
|---|---|---|---|
| ROLE-001 临床医生 | 快速理解患者、草拟文书、闭环结果和协同 | 发起授权 Agent；查看来源；编辑/接受/拒绝候选；按原流程签署或批准 | 将 AI 一键视为已确认事实；借 Agent 越权查看患者 |
| ROLE-002 护士 | 交班、任务与异常结果协同 | 使用护理范围 Skill；审阅交班/任务候选 | 将计划或建议标记成已执行护理事实 |
| ROLE-003 质控/病案/编码人员 | 发现缺陷、复核编码与整改 | 查看授权版本；处理质控/编码候选；反馈误报漏报 | 修改已签原文；把 AI 建议升级为法规硬规则 |
| ROLE-004 会诊/随访协调员 | 准备会诊、转诊、交班、随访任务 | 审阅摘要和任务候选；按授权提交 | 代替责任医生确认临床结论 |
| ROLE-005 AI 治理管理员 | 配置用例、发布、观测和停用 | 管理 Agent/Skill/Tool 候选、路由、门禁、灰度、回滚 | 单独批准自己创建的高风险版本；查看无业务必要的病历正文 |
| ROLE-006 Agent/Skill 设计者 | 沉淀可复用能力包 | 定义契约、依赖、样例和评测集 | 因创作身份获得真实患者数据或生产 Tool 权限 |
| ROLE-007 临床能力负责人 | 判断场景适用性和临床风险 | 批准用例边界、样例、严重错误定义和灰度 | 替代信息安全/隐私审批 |
| ROLE-008 安全/隐私负责人 | 审查数据边界、权限和供应链 | 批准数据分类、外部连接、红队和例外 | 独立宣告临床质量合格 |
| ROLE-009 运维/支持 | 运行观测、事件处置和恢复 | 查看脱敏轨迹；隔离组件；执行批准回滚 | 查看模型秘密或无关患者正文；修改临床结果 |

有效权限始终是“调用用户 × Agent × Skill × Tool × 机构策略 × 当前业务状态”的交集，不因作者、服务账户或模型能力扩大。

## 4. 版本范围与优先级

### 4.1 P0：首个可验证版本

| 主 Agent | 产品目标 | 自治上限 | 核心 Skill | 核心 Tool 类型 |
|---|---|---:|---|---|
| `ENCOUNTER_SUMMARIZER` | 诊前、分诊、当次、住院阶段和出院准备带来源摘要 | A1 | `encounter-previsit-summary@1`、`inpatient-course-summary@1` | 患者/就诊、文书、结果、医嘱、任务只读 |
| `DOCUMENT_DRAFTER` | 生成门诊、病程、出院、交班文书候选 | A1 | `outpatient-note-draft@1`、`discharge-summary-draft@1`、`nursing-shift-handoff@1` | 只读上下文 + `create_document_proposal` |
| `RECORD_QC` | 在硬规则之后发现语义遗漏、冲突和时序问题 | A1 | `record-semantic-qc@1` | 不可变文书、硬规则结果、知识检索、质控候选 |
| `RESULT_FOLLOWUP_COORDINATOR` | 聚合异常结果和未闭环责任 | A1；任务 A2 | `result-trend-and-followup@1` | 结果/任务只读 + `create_task_proposal` |
| `CARE_COORDINATOR` | 准备会诊、转诊、交班与随访摘要/任务 | A1；任务 A2 | `consult-referral-brief@1` | 上下文只读 + 任务/预约变更候选 |

P0 同时包含：统一入口和上下文条、运行进度与接管、来源审阅、候选差异、Agent/Skill/Tool 能力卡、评估发布、审批、观测、反馈、紧急停用和人工降级。

### 4.2 P1：完成 P0 临床灰度后

- `SAFETY_REVIEWER`：只解释确定性用药/医嘱规则和证据，不替代规则引擎。
- `CODING_ASSISTANT`：基于已签文书和有效术语版本生成编码候选。
- `PATIENT_MESSAGE_DRAFTER`：仅白名单低风险类别，红旗症状转人工。
- `AMBIENT_DOCUMENTATION`：完成显式同意、录音状态、说话人/时间引用和音频保留策略后进入灰度。
- `RESEARCH_MATCHER`：仅研究授权场景，输出条件级满足/不满足/未知，不自动入组。

### 4.3 P2 / 暂缓

- 鉴别诊断/治疗方案第二视角仅限研究或影子评估。
- 获批影像、病理、心电 AI 作为外部 Tool 接入，不在本项目重造诊断模型。
- 低风险行政自动化可评估 A3；临床动作长期以 A1/A2 为上限。

### 4.4 Agent 五层产品结构

| 层级 | 对象 | 责任 | 用户可见性 | 不承担什么 |
|---|---|---|---|---|
| L0 | `AI_MEDICAL_ASSISTANT` 统一入口 | 维护当前上下文、识别意图、选择用例和主 Agent、呈现统一审阅体验 | 始终可见 | 不产生临床结论，不直接调用临床副作用 Tool |
| L1 | 主 Agent | 对一个端到端用户任务负责；选择环节子 Agent、汇总结果、处理部分失败并交付一个最终候选 | 显示主 Agent 名称、目标和状态 | 不自行扩展场景，不把所有诊疗环节塞入一个 Prompt |
| L2 | 子 Agent | 对一个诊疗环节或独立工作单元负责；有明确输入输出、预算、状态、失败和独立 Eval | 默认在“运行详情”可见；高风险/失败时前台显著显示 | 不越过主 Agent 目标，不直接成为新的万能入口 |
| L3 | Skill | 封装模板、知识、规则编排、Schema、失败语义和评测样例 | 能力详情可见，普通用户无需手工选择 | 不拥有独立临床身份；单步转换不注册为子 Agent |
| L4 | Tool | 完成确定性查询、校验、计算、检索、保存候选或受控业务动作 | 只读调用默认折叠；副作用必须预览 | 不自主规划，不绕过领域 API、权限和状态机 |

L0–L4 之下是患者、就诊、文书、诊断、医嘱、执行、结果、任务、签署和审计等权威临床内核。任何层级的 AI 输出都不能替代这些对象的业务终态。

### 4.5 P0 主 Agent 与诊疗环节子 Agent 目录

#### 4.5.1 `ENCOUNTER_SUMMARIZER` 就诊摘要主 Agent

| 子 Agent | 适配环节 | 触发/输入范围 | 结构化输出 | 硬边界 |
|---|---|---|---|---|
| `PRE_VISIT_SUMMARIZER` | 预约后、到诊前、复诊准备 | 既往就诊、问题、过敏、当前用药、近期结果、开放任务 | 诊前摘要、近期变化、待核问题 | 不生成本次诊断或治疗计划 |
| `TRIAGE_CONTEXT_SUMMARIZER` | 门诊分诊、急诊预检 | 主诉、生命体征、既往风险、分诊事实 | 分诊上下文摘要、缺失资料、风险来源 | 分诊级别和急救触发由确定性规则/人工决定 |
| `ACTIVE_ENCOUNTER_SUMMARIZER` | 接诊中、问诊/查体后 | 当次录入、历史摘要、新结果、诊疗任务 | 当次事实摘要、新旧变化、待确认问题 | 不把未确认陈述写成事实 |
| `INPATIENT_DAILY_SUMMARIZER` | 住院每日查房前 | 上次病程后的医嘱、执行、结果、体征、护理、会诊和任务 | 24 小时/指定时窗事件摘要、趋势和未闭环项 | 不声称医嘱已执行或任务已完成 |
| `PERIOPERATIVE_CONTEXT_SUMMARIZER` | 术前准备、术后交接 | 手术申请、术前检查、风险、知情、执行事件和术后计划 | 围术期事实包、缺项和来源 | 患者/部位/侧别/核查状态以硬规则和业务状态为准 |
| `DISCHARGE_READINESS_SUMMARIZER` | 出院计划与出院前对账 | 医嘱、结果、会诊、文书、费用、用药、随访和未决任务 | 出院准备摘要、未闭环清单和责任角色 | 不决定是否准予出院，不伪造豁免 |

| `NURSING_HANDOFF_DRAFTER` | 护理班末/转单元 | 护理交班候选 | 体征、给药/治疗执行、护理计划、风险和任务 | 不把待执行计划写成已完成 |
| `DISCHARGE_NOTE_DRAFTER` | 出院/死亡终末文书 | 出院记录、小结或终末记录候选 | 入院原因、医院经过、诊断、用药、未决事项 | 未闭环事项必须显式列出；不自动签署 |

#### 4.5.3 `RECORD_QC` 病历质控主 Agent

| 子 Agent | 适配环节 | 质控范围 | 输出 | 硬边界 |
|---|---|---|---|---|
| `WRITING_QC_REVIEWER` | 书写中 | 当前草稿结构、来源、前后文 | 实时低打扰建议 | 不执行法规/机构硬阻断 |
| `PRE_SIGN_QC_REVIEWER` | 签署前 | 完整性、一致性、时序、必要来源和签署条件 | 待修改项、来源和严重度建议 | 硬规则结果单独保留且优先 |
| `ACTIVE_RECORD_QC_REVIEWER` | 运行病历抽查 | 在院/在诊文书版本、逾期、复制与诊疗一致性 | 缺陷候选和责任角色 | 不直接创建正式缺陷终态或改原文 |
| `TERMINAL_RECORD_QC_REVIEWER` | 出院/归档前 | 文书、首页、编码、结果、签名和整改闭环 | 终末质控候选和缺口清单 | 归档阻断/豁免由确定性规则和授权人决定 |
| `CORRECTION_CONSISTENCY_REVIEWER` | 更正、补充、来源报告更正后 | 新旧版本、引用来源、受影响文书 | 差异和需复核对象清单 | 不静默改写已签文书 |

质控维度中的“完整性、语义一致性、时序、复制前移、来源引用、专科约束”等是可复用 Skill；它们没有独立临床任务状态时，不单独注册成子 Agent。

#### 4.5.4 `RESULT_FOLLOWUP_COORDINATOR` 结果闭环主 Agent

| 子 Agent | 适配环节 | 触发/输入范围 | 输出 | 硬边界 |
|---|---|---|---|---|
| `NEW_RESULT_INTAKE_AGENT` | 新结果确认/回传 | 新增或更正结果、原申请、患者/就诊 | 新结果摘要、优先级依据和相关任务 | 结果确认状态以 LIS/PACS/领域系统为准 |
| `RESULT_TREND_REVIEWER` | 结果查看、查房、复诊 | 同项目/相关项目的版本化结果和单位 | 趋势、异常变化、不可比较项 | 单位/参考范围转换使用确定性 Tool |
| `CRITICAL_RESULT_CONTEXT_AGENT` | 危急值事件 | 危急值规则结果、通知/接收/处置状态 | 风险上下文和未完成状态 | 不判断危急值、不自动标记已通知或已处置 |
| `PENDING_RESULT_TRACKER` | 就诊结束、出院和随访 | 已申请未报告、部分报告、更正中结果 | 待回结果清单、责任和时限 | 不把未报告解释为阴性 |
| `FOLLOWUP_TASK_PLANNER` | 异常结果需复查/随访 | 已确认结果、已确认计划、责任策略 | 任务候选、对象、时限和证据 | 不自行决定治疗方案或发送患者消息 |
| `CORRECTED_RESULT_RECONCILER` | 报告更正/撤回 | 原结果、新版本、引用文书和已建任务 | 受影响对象、复核和撤销/更正候选 | 不修改已签文书或删除历史任务 |

## 5. 产品对象与信息架构

| 对象 | 用户可理解的定义 | 必须展示/记录的关键字段 |
|---|---|---|
| AgentDefinition | 为一个明确任务负责的受控执行者 | 名称、`MAIN/SUB` 层级、父主 Agent、适用诊疗环节、目标、角色/场景、自治等级、上下文、Skills、Tools、预算、停止/接管、输出、版本、状态、负责人 |
| AgentComposition | 主 Agent 可编排的子 Agent 有向无环组合 | 主 Agent 版本、子 Agent 白名单/版本、触发条件、输入输出映射、顺序/并行、总预算、部分失败策略、人工接管和最终聚合契约 |
| SkillDefinition | 可复用且可评测的医疗工作流包 | 用途、输入/输出 Schema、前后置条件、模板/知识、允许 Tools、失败语义、依赖、Evals、版本、许可证 |
| ToolDefinition | 单一职责的确定性能力 | 只读/候选/副作用等级、输入输出、患者范围、权限、幂等、超时、错误、补偿、审批策略、版本 |
| UseCasePolicy | 某机构/科室/角色对某能力的准入规则 | 场景、数据分类、模型路由、Agent/Skill/Tool 版本、自治上限、阈值、静默/停用、有效期 |
| ContextLease | 一次运行可读取的最小上下文租约 | 主体、机构、患者、就诊、任务、字段范围、来源、版本/水位、过期时间、撤销原因 |
| AgentRun | 一次可追踪、可取消、可恢复的主/子 Agent 运行 | run_id、parent/root run、agent level、调用者、上下文、制品版本、步骤、预算、状态、错误、审批、来源、结果、时间 |
| AIProposal | 与临床事实分离的候选结果 | 类型、患者/就诊、来源、生成版本、差异、不确定项、状态、审阅人、接受/拒绝/过期原因 |
| ActionApproval | 对屏幕所示具体副作用的逐次批准 | 动作、对象、参数、证据、风险、批准人、有效期、payload hash、状态 |
| ActionExecution | 批准后由领域内核执行的结果 | approval_id、幂等键、执行身份、业务结果引用、状态、失败/补偿、核验时间 |
| EvalEvidence | 能力上线与继续运行的证据 | 数据集版本、场景、错误分级、指标、样本量、审阅者、结果、门禁、适用范围、有效期 |

前台信息架构保留“AI 医助小南”统一入口；完整工作区分为“当前任务、诊疗阶段/子任务、来源、候选、运行记录”五区。临床用户默认看到主 Agent 和当前环节；可展开查看子 Agent 的输入范围、状态、结果和失败，但不必理解底层 Skill/Tool 编排。Agent/Skill/Tool 管理进入 AI 治理中心。

## 6. 核心流程与状态

### 6.1 FLOW-01 临床用户发起与审阅

1. 用户从患者页面、任务页、文书页或全局入口发起任务。
2. 系统展示并校验机构、角色、患者、就诊、任务和页面上下文；无患者时进入安全空上下文。
3. 路由到一个已批准主 Agent，固定主 Agent、AgentComposition 和 ContextLease 版本。
4. 主 Agent 根据诊疗环节选择白名单子 Agent；每个子 Agent 获得更小的上下文、预算和允许 Skill/Tool，并形成父子运行轨迹。
5. 主 Agent 汇总子 Agent 的完整、部分或失败结果；用户可查看阶段进度、取消整个任务或接管具体环节。
6. Verification 步骤检查父子 Schema、来源、患者一致性、冲突、预算和政策。
7. 最终结果以一个主 AIProposal 展示来源、不确定项、子任务状态和与当前内容的差异。
8. 用户接受、修改后接受、拒绝或返回人工流程；进入签署/执行的仍走原领域状态机。

### 6.2 FLOW-02 候选动作审批与执行

1. Agent 只能生成动作预案，不能直接产生临床副作用。
2. 审批页展示患者/就诊、对象、关键参数、证据、风险、后果、有效期和差异。
3. 审批人重新鉴权并批准或拒绝；提案者不得自批高风险动作。
4. 执行端重新鉴权、校验上下文和 payload hash，通过领域 API 幂等执行。
5. Agent 读取业务结果进行核验；不能核验则显示“执行状态未知”，进入人工对账。

### 6.3 FLOW-03 能力设计与发布

候选定义 → 契约校验 → 合成数据测试 → 权限/跨患者/提示注入/工具故障红队 → 临床评审 → 安全评审 → 影子 → 灰度 → 批准 → 持续监测。任一硬门禁失败均不得晋升。

### 6.4 FLOW-04 故障、取消与恢复

- 模型/Tool 超时：展示具体失败阶段；只读步骤可按策略重试，副作用不得盲重试。
- 用户取消：停止后续步骤，保留已发生的可审计事实；未完成候选不进入病历。
- 上下文变化：立即过期旧 ContextLease、审批和候选；重新发起后不得复用旧批准。
- 恢复：固定原制品版本，重新鉴权和读取权威事实；已成功副作用按幂等键跳过并核验。
- AI 全部不可用：原有人工登记、文书、医嘱、执行、签署和任务流程仍可完成。

### 6.5 FLOW-05 主 Agent 编排子 Agent

1. 主 Agent 读取当前诊疗环节、页面对象、用户目标和已批准 AgentComposition。
2. 只选择该主 Agent 版本白名单内的子 Agent；生成可解释的阶段计划和总预算。
3. 为每个子 Agent 派生不大于父级的 ContextLease、权限、时间/成本/Tool 预算和幂等范围。
4. 子 Agent 独立运行并返回结构化状态：`COMPLETE`、`INCOMPLETE`、`NO_EVIDENCE`、`BLOCKED` 或 `FAILED`。
5. 主 Agent 按组合契约决定继续、跳过非关键子任务、等待人工补充、取消后续步骤或整体失败。
6. 主 Agent 只能在所有关键子任务和最终 Verification 通过后生成主 AIProposal。
7. 取消父运行必须传播到所有未完成子运行；恢复时逐个核验原子运行和副作用，不得重跑已成功副作用。

### 6.6 状态机

**AgentRun：** `CREATED → ROUTING → RETRIEVING → PLANNING → GENERATING → VERIFYING → READY_FOR_REVIEW → COMPLETED`。

旁路状态：

- 需逐次审批：`PLANNING → WAITING_APPROVAL → GENERATING`。
- 用户接管/拒绝/过期：任一可取消状态 → `CANCELLED`；`WAITING_APPROVAL → CANCELLED`。
- 验证失败：`VERIFYING → BLOCKED`；修复上下文后创建新运行，不原地篡改结果。
- 系统失败：运行态 → `FAILED`；仅符合幂等和恢复策略时进入 `RECONCILING` 后继续。

**子 AgentRun：** `CREATED → QUEUED → RUNNING → COMPLETE | INCOMPLETE | NO_EVIDENCE | BLOCKED | FAILED | CANCELLED`。子 Agent 的 `COMPLETE` 仅表示其结构化子任务完成，不代表主任务完成或任何临床事实生效。

**父子聚合：** 关键子 Agent `BLOCKED/FAILED` 时，父运行不得进入 `READY_FOR_REVIEW`；非关键子 Agent 失败仅在组合契约明确允许时进入 `PARTIAL` 聚合，并在用户界面显著列出缺失范围。

**AIProposal：** `DRAFT → READY_FOR_REVIEW → ACCEPTED | REJECTED | EXPIRED`；被接受的内容仅进入目标领域的草稿/候选状态，不直接成为签署事实。

**Agent/Skill/Tool 版本：** `DRAFT → CANDIDATE → VALIDATED → APPROVED → SUSPENDED | RETIRED`；`CREATED` 仅表示制品已生成，`VERIFIED` 必须有测试证据。

## 7. 业务规则

| ID | 规则 |
|---|---|
| BR-001 | Agent 是受控任务执行者，不具备医疗执业、签署或最终决策身份。 |
| BR-002 | 临床 AI 默认自治上限为 A1；结构化候选可到 A2，但必须由授权人员逐项确认并由领域内核执行。 |
| BR-003 | A4 自主诊断、处方、签署、治疗、执行和解除阻断一律 `DENY`。 |
| BR-004 | 每个用户任务只绑定一个主 Agent 和一个可理解目标；子 Agent 与 Skill 组合不得改变主目标或扩大范围。 |
| BR-005 | 前台统一入口不得形成通配权限；每次运行必须绑定当前机构、主体、患者/就诊或明确安全空上下文。 |
| BR-006 | 切换患者、就诊、岗位、机构、任务或页面关键对象后，旧 ContextLease、审批和候选立即失效。 |
| BR-007 | 事实性临床结论必须可回到具体来源和版本；证据不足时输出“无足够证据/未知”，不得补写。 |
| BR-008 | AIProposal 与临床事实、已签文书、已确认诊断、已生效医嘱和已完成任务分层保存。 |
| BR-009 | 接受候选不等于签署或执行；后续仍使用原业务权限、校验、签署和状态机。 |
| BR-010 | 硬规则、确定性 Tool 结果和 AI 建议必须视觉及数据分层；AI 不得降低硬规则严重度。 |
| BR-011 | Tool 必须采用强 Schema 和白名单；禁止向 Agent 暴露通用 SQL、通用 HTTP、任意文件或任意代码执行。 |
| BR-012 | Tool 执行端必须独立鉴权、校验患者/就诊和业务状态，不信任提示词或服务账户声称的权限。 |
| BR-013 | 有副作用 Tool 必须声明风险、幂等、超时、失败、补偿、核验和审批；缺一不得发布。 |

## 9. 验收标准

| ID | Given / When / Then |
|---|---|
| AC-001 | **Given** 用户在门诊患者 A 页面打开医助，**When** 切到患者 B 或安全空上下文，**Then** 患者 A 正文、建议、审批和可执行动作全部不可见且不可提交，入口显示新上下文。 |
| AC-002 | **Given** 用户输入超出批准用例或包含多个患者的模糊请求，**When** 系统路由，**Then** 不创建高风险运行，展示澄清或可选任务，不泄露患者存在性。 |
| AC-003 | **Given** AgentRun 正在调用多个只读步骤，**When** 用户取消，**Then** 后续 Tool 不再调用，运行变为 `CANCELLED`，已完成只读轨迹可审计且无候选自动落库。 |
| AC-004 | **Given** 摘要包含诊断、用药、结果或任务事实，**When** 用户点击来源，**Then** 可定位到同患者/就诊的具体对象、版本和时间；来源不可用项明确标记未验证。 |
| AC-005 | **Given** AIProposal 已生成，**When** 用户接受、修改或拒绝，**Then** 分别保留原候选、人工差异和处理结果；接受后仍停留在目标领域草稿/候选状态。 |
| AC-006 | **Given** 模型和 Agent 服务全部不可用，**When** 用户继续病历书写、医嘱、签署或任务处理，**Then** 原人工主链可完成，页面不把故障结果显示为完整答案。 |
| AC-007 | **Given** 某来源延迟或相互冲突，**When** 生成就诊摘要，**Then** 输出为 `INCOMPLETE`，并列冲突和缺失，不自动选择一个结论。 |
| AC-008 | **Given** 文书输入缺少查体或执行证据，**When** 生成草稿，**Then** 对应段落显示未确认/缺失，不生成虚构正常值、已执行事实或签名。 |
| AC-009 | **Given** 硬规则命中高严重度缺陷，**When** RecordQC 给出不同意见，**Then** 硬规则仍单独展示且严重度不降低，AI 仅以建议层呈现。 |
| AC-010 | **Given** 危急值已确认但通知状态缺失，**When** 结果闭环 Agent 运行，**Then** 显示危急值来源和“通知状态未知”，只生成任务候选，不声称已通知。 |
| AC-011 | **Given** 会诊任务计划已获预览，**When** 患者、目标团队或关键参数变化，**Then** 旧计划和批准过期，任何提交都要求重新确认。 |
| AC-012 | **Given** Skill 缺少失败语义、评测集或责任人，**When** 设计者提交候选，**Then** 发布被阻止并指出缺失字段。 |
| AC-013 | **Given** 已批准 Skill 的输出不符合 Schema 或依赖版本漂移，**When** 运行验证，**Then** 结果不进入 `READY_FOR_REVIEW`，运行标记 `BLOCKED` 并可追踪原因。 |
| AC-014 | **Given** Skill 组合存在循环、权限扩大或数据模式不匹配，**When** 解析依赖，**Then** 不能发布，管理界面显示具体冲突路径。 |
| AC-015 | **Given** 专科包尝试复制核心患者对象或关闭平台保护规则，**When** 提交验证，**Then** 静态门禁拒绝且不能通过普通例外绕过。 |
| AC-016 | **Given** Tool 暴露通用 SQL/HTTP、通配权限或缺少副作用幂等，**When** 提交发布，**Then** Tool 不能进入 `APPROVED`。 |
| AC-017 | **Given** 用户对某字段无权或 ContextLease 已撤销，**When** Agent 调用只读 Tool，**Then** 执行端拒绝或裁剪字段，不返回该数据也不泄露其存在性。 |
| AC-018 | **Given** 同一 run、proposal type 和 payload hash 重复请求，**When** 创建文书/任务候选，**Then** 返回同一 proposal，不产生重复记录或临床事实。 |
| AC-019 | **Given** 一个副作用动作已批准，**When** payload、权限、业务状态或有效期任一变化，**Then** 执行端拒绝；重复回调不重复副作用，失败显示真实状态并进入对账。 |
| AC-020 | **Given** Agent 定义缺少单一目标、预算、停止或接管条件，**When** 提交候选，**Then** 不能进入评估阶段。 |
| AC-021 | **Given** 候选版本在跨患者、提示注入、来源或严重临床错误测试中任一失败，**When** 申请灰度，**Then** 灰度被阻止且保留失败证据。 |
| AC-022 | **Given** 同一 Agent 切换模型、Skill 或 Tool 版本，**When** 管理员查看效果，**Then** 指标可按具体版本拆分，不把不同版本混成一个总体数字。 |
| AC-023 | **Given** 用户提交“患者错误”反馈，**When** 系统接收，**Then** 关联运行被标记安全事件，阻止继续使用相关候选，并进入责任队列。 |
| AC-024 | **Given** 某 Tool 被紧急停用，**When** 新运行或在途运行到达该 Tool，**Then** 新调用被拒绝、在途运行进入安全终态，人工流程仍可用且恢复需重新验证。 |
| AC-025 | **Given** 科室策略试图放宽平台 A4 禁止或跨患者规则，**When** 发布，**Then** 系统拒绝并展示平台保护规则来源。 |
| AC-026 | **Given** 当前 6 个前台 Agent 完成目录迁移，**When** 用户从旧入口发起任务，**Then** 可看到实际路由的主 Agent、诊疗环节和子 Agent 组合；实验能力不因旧状态自动进入生产批准。 |
| AC-027 | **Given** 一个候选能力只有单步模板转换且没有独立状态、预算或恢复，**When** 设计者尝试注册为子 Agent，**Then** 系统阻止并提示应建为 Skill；满足六项子 Agent 条件时才能进入候选。 |
| AC-028 | **Given** 用户分别在门诊接诊、急诊预检、住院查房和出院准备页面请求“总结患者”，**When** 系统路由，**Then** 显示同一主 Agent 下不同的环节子 Agent 组合，且切换工作域后旧组合失效。 |
| AC-029 | **Given** AgentComposition 含循环、未批准动态子 Agent、无总预算或未定义关键子任务失败策略，**When** 提交发布，**Then** 发布被阻止并展示具体节点和冲突路径。 |
| AC-030 | **Given** 父运行只允许当前住院就诊和只读结果，**When** 子 Agent 请求跨患者资料或任务写入 Tool，**Then** 子运行被拒绝并标记 `BLOCKED`，父运行不能把该输出用于候选。 |
| AC-031 | **Given** 一个主 Agent 包含两个关键和一个非关键子 Agent，**When** 关键子 Agent 失败，**Then** 父运行 `BLOCKED`；当非关键子 Agent 失败且组合明确允许时，父结果标记 `PARTIAL` 并显著列出缺失范围。 |
| AC-032 | **Given** 当前处于出院准备且存在未报告结果和未签文书，**When** EncounterSummarizer 运行，**Then** 只调用批准的 DischargeReadiness 等子 Agent，列出未闭环项，不输出“可以出院”的决定。 |
| AC-033 | **Given** 用户从主任查房任务发起文书草拟，**When** DocumentDrafter 编排，**Then** 使用 WardRoundNoteDrafter 而非普通日常病程子 Agent，并保留实际查房者、记录者和待补上级意见。 |
| AC-034 | **Given** 同一文书分别处于书写中、签署前和归档前，**When** RecordQC 运行，**Then** 路由到对应生命周期子 Agent，使用相应规则语义，且任何 AI 结果都不能降低硬规则严重度。 |
| AC-035 | **Given** 报告被更正且旧结果已被文书引用并生成随访任务，**When** ResultFollowupCoordinator 运行，**Then** CorrectedResultReconciler 列出受影响文书和任务候选，不覆盖已签文书、不删除历史任务。 |
| AC-036 | **Given** 转科交接仍有未完成医嘱、结果和护理任务，**When** CareCoordinator 运行，**Then** TransferHandoff 和 TaskReconciliation 子 Agent 分别输出交接与任务差异，由主 Agent 聚合并保留接收方未确认状态。 |

## 11. 数据、事件与隐私契约

### 11.1 最小数据字段

每次运行至少记录：`tenant_id`、`actor_id/role`、`patient_id`（安全空上下文可空）、`encounter_id`、`task/page context`、`clinical_stage`、`root/parent/run_id`、`agent_level`、`agent/version`、`composition/version`、`skills/versions`、`tools/versions`、`model route/version`、`policy/version`、`context lease/hash/expiry`、`run state`、`budget usage`、`source refs`、`proposal/approval/execution refs`、`errors`、`feedback` 和时间戳。

不得默认记录：模型隐藏思维链、无必要的完整病历副本、明文秘密、未经批准的原始音频或跨患者长期记忆。

### 11.2 核心事件

- `ai.run.created|started|blocked|cancelled|failed|completed`
- `ai.subrun.queued|started|complete|incomplete|no_evidence|blocked|failed|cancelled`
- `ai.composition.selected|partially_completed|blocked|replanned`
- `ai.context.issued|expired|revoked|mismatch_detected`
- `ai.tool.requested|denied|succeeded|failed|reconciled`
- `ai.proposal.created|reviewed|accepted|rejected|expired`
- `ai.approval.requested|approved|rejected|expired`
- `ai.execution.started|succeeded|failed|unknown`
- `ai.component.approved|suspended|retired|rolled_back`
- `ai.feedback.created|triaged|resolved`
- `ai.safety.cross_patient_detected|unauthorized_action_detected`

所有事件必须含机构、用例、运行、制品版本和必要业务对象引用；运营指标与患者级轨迹分权展示。

### 11.3 保留和训练边界

- ContextLease 与缓存按最短业务必要期限保存，过期后不可继续调用 Tool。
- 反馈不得默认进入外部模型训练；用于内部评测或微调须另有批准用途、去标识策略和数据版本。
- 原始音频、转写、提示和模型响应分别配置保留策略；P0 不默认采集环境音频。

- 草稿打开率、完成率、直接采纳率、采纳后修改率、拒绝/接管率。
- 质控误报、漏报、整改完成和硬规则影响。
- 结果闭环从确认到责任接受/完成的时长与逾期率。
- 主动提醒量、重复率、忽略率、每班次打断和高严重度漏报。
- 运行成功、Tool 失败、模型切换、成本、延迟和事件恢复时间。
- 诊疗环节路由准确率、人工改选率、子 Agent 启动/跳过/部分完成/失败率和父子预算放大系数。
- 各子 Agent 对主结果的有效贡献、重复输出、冲突率及因内部拆分增加的净等待/复核负担。

采纳率不得单独作为成功标准。收益目标在得到本地基线、科室差异和置信区间后由产品与临床共同批准。

## 16. Definition of Ready / Done

### 16.1 进入原型和 HLD 前（Ready）

- P0 场景、角色、输出和自治等级获得产品与临床负责人确认。
- Q-001–004 至少形成首个试点的临时决策。
- 每个 P0 主 Agent 及首批子 Agent 的诊疗环节、输入来源、关键性、禁用条件、严重错误和人工降级路径明确。
- Q-009–011 对首条试点环节链形成临时决策。
- Tool 被分类为只读、候选或副作用；副作用标出领域责任人。

### 16.2 宣称功能完成前（Done）

- 需求、原型、API/Schema、数据、权限、状态、事件和 AC 可双向追溯。
- AC-001–036 与 NFR 硬门禁通过；真实领域动作需端到端验证，不能只验证状态表。
- 临床评测含错误分级、亚组、双人复核、版本和适用范围。
- 影子/灰度、停用、回滚、故障、人工接管和事件处置均有证据。
- 用户文案始终使用“候选、草稿、建议、未确认”，不宣传为自主诊疗能力。
