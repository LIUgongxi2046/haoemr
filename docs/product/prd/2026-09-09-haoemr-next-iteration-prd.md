## 最新约束：在原系统内迭代

用户明确要求保持原架构和设计风格，优先融合系统管理。经核对现有代码，本轮全部管理需求可以由原入口承接：**主菜单新增 0、系统管理二级导航新增 0、独立系统新增 0**。保留原组织树、模板管理、参数配置、任务与审计；包导入仅增加页内标签及管理弹窗。原型默认打开原系统管理工作台，撤回 v0.1 的欢迎首页、16 屏侧栏及自定义字号/按钮配色。

完整复用依据与宿主映射见[原系统融合修订](../../design/ui-delivery/iteration-20260909/integration-revision.md)。该修订优先于 v0.1 的推导。只有既有入口无法承接且有明确证据时才考虑用户允许的单一备用主菜单，本期无需启用。

保留 Spring Boot 模块化单体、PostgreSQL、JdbcClient/显式 SQL、Flyway、Vue 单入口及原 OpenAPI、上下文授权、审计/Outbox。安装器是缺失能力补充，不复制组织、模板、能力包或任务引擎。

## 0. 设计范围与决策摘要

承接用户“评估迭代方向”及“制定详细的需求设计和 UI 设计”的要求。本次设计覆盖五个方向：稳定基线、安装交付、医生效率、AI 辅助、单院单科试点。R1 优先交付稳定基线和干净安装；R2、R3 形成可评审的需求与页面设计，依赖到位后分别排期。本次仅新增设计资产，不修改业务代码、数据库、生产配置或已有封板记录。

**本期主结果：部署人员能按文档创建一个无临床业务数据的机构，安装一个病历模板包，完成独立审批，并进入可理解的空工作台。** 稳定基线作为前置工程验收，不新增面向医生的“测试大屏”。

设计资产：`docs/design/ui-delivery/iteration-20260909/`。离线交互原型：`prototype/iteration-20260909/prototype.html`。所有演示状态、机构、患者、计数和测试结果均为合成设计样例。

编号命名空间为 `ITER-FR/BR/AC/NFR/Q/RISK`，避免与原 v1.0、知识中心 PRD 重号。

## 4. 范围边界

R1 包含一个门诊基础模板包；演示数据独立、只能用于隔离演示环境。正式包安装得到配置草稿，不自动发布。升级预检和冲突展示在首版设计范围内，扩展大包、护理/专科/AI 包在 R2 后逐包推进。

不包含：重建已有临床模块、按选装模块删建数据库表、微服务改造、全院 HIS 替代、自动清库、全量专科扩张、公开插件市场、在线付费、自动诊断/处方、无权限的真实患者数据处理。稳定性工作不变成无限全菜单巡检。

### 5.1 输入与导入细则

机构编码首次确认后只读；修改需走既有机构治理。首版可添加一个院区、至少一个业务科室，组织树导入放后续。名称去首尾空白、保留中文，不从名称推导真实机构身份。

首包采用受约束的数据文件容器（建议 ZIP 内 manifest.json + JSON/CSV），文件大小建议不超过 10 MB、解包后 50 MB、500 个条目；这些是待压测的设计上限。拒绝路径越界、递归压缩、超限、重复条目、未知字段类型和可执行内容。大小限制由服务端执行，前端提示不替代校验。

来源可信须来自部署方认可的包分发/签名机制；本期不设计“一键忽略来源风险”。设计样例明确为非生产包。正式包来源待确定不会阻塞原型评审。

## 7. 状态与流程

### 7.1 初始化

初始化检查展示“未引导 / 已引导 / 组织待补齐 / 组织已就绪”，由部署结果与既有组织对象推导；这些是检查结果，不新增组织生命周期或第二份机构资料。

- 未初始化：部署负责人按未来已验收部署说明执行受控引导；此时不承诺浏览器已可用。
- 已引导：通过认证进入原系统管理工作台，管理员身份与机构绑定只读可核对。
- 组织待补齐：定位原组织机构页面；已保存节点按既有组织生命周期处理，未保存表单沿用原退出规则。依赖缺失仅阻断对应业务操作，不引入全系统停用开关。
- 机构完成：进入模块安装；机构完成与临床可用是两个独立结论。
- 引导重复、并发失败：读取已完成结果或真实失败记录，禁止创建第二个管理员。

### 7.2 安装操作与配置发布

预检：`NOT_CHECKED → CHECKING → READY / BLOCKED / STALE`。

安装：`QUEUED → INSTALLING → SUCCEEDED / FAILED_ROLLED_BACK / RECOVERY_REQUIRED`。重复安装可直接得到 `ALREADY_INSTALLED`；入队前可取消，执行后仅允许离开页面继续查询，不设计虚假取消。

配置发布逐域沿用现有流程，不新增统一审批状态机。首包模板使用现有 DRAFT→另一名授权管理员执行“审批发布”→PUBLISHED；模板停用、新版本修订保持原机制。其他配置仍遵循自身实际状态机。`SUCCEEDED` 的界面标题必须为“安装完成，待审核启用”，不能写“业务已上线”。

恢复异常不出现“安全重试”按钮直到回滚状态确认。页面断线导致结果未知时先查询原操作，再决定重试，不发第二笔安装。

### 7.3 首次交付主流程

部署前提核对 → 一次性引导 → 认证登录 → 确认机构/院区/科室 → 查看模块就绪度 → 选择基础模板包 → 查看内容与许可 → 预检 → 核对差异 → 确认安装 → 进度 → 安装记录详情 → 原模板输出执行独立审批发布 → 原工作台空态。

恢复分支：缺依赖返回包列表；来源/文件损坏重新选包；组织变更重跑预检；失败后确认回滚再重试；成功后关页可从安装记录返回；独立发布前不满足条件则保留原草稿，仍通过原模板修订用例处理，医院现有已发布版本继续有效。

### 7.4 医生与 AI 后续流程

就诊列表 → 当前患者/就诊条 → 模板或继续草稿 → 保存 → 内嵌规则检查 → 定位问题并修订 → 重新检查 → 原有签署流程。病人切换且有未保存修改时提供“保存并切换 / 放弃本次编辑 / 留在当前页”。AI 入口位于编辑区辅助面板；候选→查看依据→逐项采用→草稿修改；同一患者的新版本也须重新核验，不能只校验患者 ID。

## 10. UI 与数据反馈约定

固定表述：“机构设置完成”“预检通过”“安装完成，待审核启用”“检查已失效”“正文已保存，规则检查暂不可用”“结果暂不可确认，正在查询原安装记录”。禁用模糊的“系统已就绪”绿勾取代模块条件。

无权限不得呈现 0 条患者/0 项待办；有权限且无数据才显示空态。部分来源失败只影响相应区域，保留已授权内容。不可操作按钮旁须解释条件，不能仅依赖 hover。所有确认显示机构、版本、变更数量、是否生成草稿、后续审核步骤。

稳定基线仅保留工程验收文档，不作为新产品页面。原型仅在管理页面内展示新增区域；交互编号是文档索引，不是导航或根路由。

## 12. 下游交接与完成定义

产品评审确认 R1 范围、包内容和角色职责；UI 评审先核对现有主导航及系统管理二级导航逐项一致，再核对页内主路径、失败恢复、手机布局。架构阶段处理引导入口、安装原子性、迁移策略与接口契约，本 PRD 不预造可调用 API。实施按 R0→R1 的端到端切片推进，复用既有组织、能力包、模板、授权和审计服务。

R1 验收必须覆盖：空库→机构→首包→独立审核→空工作台；同包重复提交；跨租户拒绝；缺依赖、损坏包、预检失效；安装失败及断线恢复；医院修改冲突；旧库升级；正式环境演示包拒绝。所有检查绑定同一候选版本。页面可点击、连真实服务、状态正确与数据结果一致才算实施完成。

本次产物完成定义仅为文档/追溯表/可点击设计原型/视觉资产创建并验证；设计建议仍待评审，不修改原项目封板结论。
