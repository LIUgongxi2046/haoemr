## 1. 结论与迭代目标

本轮目标不是推倒重来，也不是继续堆页面或 CRUD，而是在保护现有稳定功能的前提下，让遗漏的页面能力、业务对象和 AI 候选形成可验证闭环：

1. 把交接/自查文档确认的 demo 功能完成为真实可用闭环：`clinical` 门户指标接真实聚合、`unified-home` 完成真实角色聚合、退役仿真入口接入已有真实能力或补齐缺失链路、mock 总览调用真正可用；不允许通过删除、隐藏或改名消除 finding。
2. 把诊疗执行、任务提醒、AI、数据、知识、配置和专科域的 OPEN 项推进到业务终态。非 demo 的纯治理/只读页如确无运行时职责，只能在产品明确决策后固化定位；不得用此例外规避 demo 功能开发。
3. 建立覆盖全部合同路由、动态深链、关键状态、关键角色、弹窗和多视口的 UI 细节证据矩阵；保留开发过程中已经形成的整体设计，只修功能按钮、间距、字体、对齐、响应式和状态反馈等问题。
4. 让 Medical Agent Harness 的发布、运行、预算、工具、候选、审批和执行证据成为一条连续链路；DeepSeek 只作为可替换模型 Adapter，不成为权限主体或临床事实来源。
5. 完成全量 S009 功能与回归门禁、S010 安全门禁后，重新给出本地/影子/生产三级结论。
6. 任何修复都先复用现有 API、Service、状态机、表、路由、组件和测试；只有现有结构无法满足明确验收条件时，才允许最小兼容扩展。

本地闭环完成不等于生产可上线。真实 OIDC/MFA、CA/TSA、LIS/PACS/医保/HIS、设备网关、消息通道、支付、WORM/对象存储和正式模型临床评测仍属于外部轨道；这些未完成前，整体生产门禁保持 `NO-GO`。

### 2.3 本轮统一完成定义

一个功能任务只有同时满足下列条件才可标记 `VERIFIED`：

1. 修改前先记录受影响模块现有绿测、页面行为和数据契约；修改后这些既有能力继续通过，且未改变未授权行为。
2. 使用同一患者/就诊/业务主键完成跨页面或跨服务流转，并到达预期终态。
3. 失败、越权、重复提交、版本冲突和外部不可用均有确定性行为；医疗历史不得被无审计物理删除。
4. 后端定向测试、前端测试、生产构建、浏览器真实交互和证据报告全部通过。
5. 如果涉及配置，至少有一个运行时消费者；非 demo 的纯治理页如果没有消费者，必须经明确产品决策后标为“治理台账/未启用”，不得把该例外用于 demo 功能。
6. 如果涉及 AI，必须保留输入范围、模型路由、Tool 调用、预算、候选 payload hash、审批、核验和审计证据；模型文本不得直接改写临床真相。
7. 文档、路由契约、OpenAPI、生成代码和菜单名称同步，无手填数量漂移。
8. 交接/自查中标记为 demo、hybrid 且含演示轨、静态壳或主按钮未接线的功能，必须提供真实 API/持久化/状态迁移/下游消费证据；受控仿真功能则必须在仿真边界内完成全流程、失败留证和数据源标记。

## 3. 范围、假设与非目标

### 3.1 本轮范围

- 09-04 自查报告中的全部 P1/P2/P3 本地缺口。
- 09-04 交接/自查中发现的全部 demo 功能与演示感残留，列为必须完成范围，不接受删入口、隐藏、禁用或只改文案作为闭环。
- 当前全部合同路由、菜单入口、动态深链、共享 shell、全局 Eva 入口和关键业务弹窗的 UI 细节自查及修复；以功能按钮对齐、间距、字体、文案、状态反馈、遮挡和响应式为主。
- 角色至少覆盖：医生、护士/护士长、药师、医技、质量/病案、系统/安全管理员；具体账号由可重复 fixture 生成。
- 视口至少覆盖：1440×1000、1280×800、1024×768、390×844。
- 页面状态至少覆盖：正常数据、空态、加载、后端失败/失败关闭、长文本/大数据、无权限；可写页面另覆盖新建、编辑、逻辑删除/取消、确认和版本冲突弹窗。

### 3.2 假设

- 继续使用 Spring Boot 单体、PostgreSQL/Flyway、Vue 3、生成契约和现有审计/Outbox 模型，不做框架迁移。
- 开发/验收数据均为脱敏合成数据，不引入真实患者 PHI。
- UI 以当前代码中的最新界面和已稳定共享组件为权威基线。历史原型只用于核对遗漏功能、按钮语义或明确回归，不要求一比一恢复旧版布局。
- DeepSeek Harness 仅作为架构参考；项目继续维护供应商无关的 Medical Agent Harness，不直接耦合预览期包名/API。

### 3.3 非目标

- 不在本轮擅自接入医院真实凭据、生产患者数据、生产消息通道或真实支付。
- 不为追求“全 CRUD”物理删除医疗证据；删除语义必须按领域使用撤销、冲正、作废、停用或归档。
- 不做无关框架升级、大范围重构、微服务拆分或新增菜单。
- 不进行页面整体重设计、导航结构重排、主题换肤、大面积配色调整或为了匹配旧原型而回退现有设计。
- 不替换已经稳定的模块、Service、状态机、数据表或 API；不以“统一架构”为由重写已通过验收的业务链。
- 不进行无缺陷证据支撑的目录搬迁、公共接口改名、数据库重新建模、组件体系替换或批量代码风格重写。
- 不把 commit、push、生产迁移、部署、客户端上传或外部审核合并成一个“发布”动作。

### 3.4 增量补缺原则

1. **先证明缺口**：每项实现前必须将自查结论与当前代码、页面和数据库再次核对；如果现有功能已经闭环，只补测试/文档，不重复开发。
2. **先锁定稳定行为**：复用现有定向测试和浏览器脚本建立修改前基线；没有覆盖时先补 characterization test，再修改实现。
3. **最小纵向补丁**：优先增加校验、状态迁移、消费者、按钮接线或小型 Adapter；不替换整层实现，不复制第二套并行体系。
4. **保持兼容**：公共 API、路由、数据库字段和已有数据默认向后兼容；确需扩展时优先新增可选字段、兼容读取和分阶段约束。
5. **限制影响面**：每个任务明确允许修改目录和核心符号；超出范围的新问题回到台账另建任务，禁止顺手重构。
6. **小批回归**：每个最小补丁完成后先跑受影响回归，再合并成候选批次跑全量；发现稳定功能回归立即停止扩展并回退最小改动。
7. **删除与替换需证据**：只有确认入口退役、无运行消费者、无数据依赖且有回滚方案时，才允许删除；否则采用停用、兼容或明确标注。
8. **demo 闭环不可降级**：交接/自查已点名的 demo 功能不适用“删除、停用或改文案即完成”。若同等真实能力已在其他页面/Service 存在，必须复用该能力并接通原入口与完整业务路径；确实缺失时才作最小增量开发。
9. **单一代码归属**：每个缺口只设一个功能实现任务；UI 验收、回归和安全任务只发现/验证问题，修复必须回到所属功能任务重验，不另建平行实现。

## 5. 全页面 UI 细节自查与修复方案

### 5.0 设计边界

- 当前运行界面是本轮设计基线。开发过程中已经形成的新信息架构、页面结构和交互方式默认保留。
- 历史原型仅作为功能清单和回归参考：用于发现遗漏按钮、错误入口、错误文案或明确功能缺失，不作为像素级复刻目标。
- 默认只允许局部修复：按钮可见性/位置/禁用条件、操作分组、字体字号/字重/行高、模块间距、对齐、表格密度、长文本换行、弹窗尺寸、状态提示、移动端遮挡和焦点行为。
- 只有当前布局导致功能不可达、严重遮挡、明显信息层级错误或跨页面核心流程中断时，才允许最小范围结构调整；调整原因和受影响页面必须写入 finding。
- 截图用于记录修复前后和跨视口复核，不设置“一比一匹配旧原型”的像素差异门禁。

### 5.1 覆盖台账

由代码自动生成 `page-state-coverage.json/csv`，至少合并以下来源：

1. `contracts/generated/route-contract.generated.json` 的全部 route ID。
2. `web/src/vue/router.ts` 的带参数深链与别名。
3. `ClinicalShell.vue` 的一级/二级菜单入口和模拟接口子菜单。
4. `web/src/vue/views` 视图文件与共享可路由组件。
5. 关键弹窗、抽屉、AI center/side panel、空态/错误态/无权限态。

每一行至少记录：`page_id`、route/参数 fixture、所属域、角色、患者/就诊前置、视口、状态、关键操作、截图、finding、修复 commit、复测证据。登录页是否计入合同路由必须在此固定，从根源解决 198/199 与 200/201 的统计差异。

### 5.2 自动检查维度

- 路由渲染、唯一 H1、唯一主内容 landmark、一级/二级菜单激活状态。
- 页面级横向溢出、弹窗越界、sticky/fixed 遮挡、按钮/表单重叠、表格仅容器内滚动。
- 字体族、字号、字重、行高、页面头、卡片间距、按钮尺寸和响应式断点与当前设计 token 一致。
- 功能按钮与实际能力一致：必需操作不缺失、不重复、不放错区域，禁用原因明确，点击后进入正确弹窗、页面或业务状态。
- 长中文、长英文/技术编码、空值、极大数量、错误消息不会撑破布局。
- 控件有可访问名称；Tab 顺序、Escape 关闭、焦点回归、弹窗焦点约束可验证。
- loading/empty/error/fail-closed 状态不闪烁、不保留旧患者数据、不泄漏上一上下文。
- 控制台 error/warning、pageerror、4xx/5xx、失败资源请求全部归档并分级。
- 只点击安全的只读操作做通用覆盖；会改变状态的按钮必须使用隔离 fixture 和专用业务脚本。

### 5.3 修复顺序

1. 先统一 `ClinicalShell`、页面头、通用卡片/表格/表单/弹窗、状态页、Eva 容器的按钮、字体、间距、对齐和状态反馈细节。
2. 再按临床、执行/任务、AI、数据/知识/配置、质量/病案、专科、系统/模拟接口分域修复。
3. 同一 finding 在 3 个及以上页面出现时，禁止逐页复制 CSS；必须回到共享组件或 token 修复。
4. UI 细节修复不得重做整体页面、改变临床状态机、权限、数据删除语义或外部 fail-closed 行为。
5. 每个分域修复必须同时跑桌面、平板宽度和手机视口；最终全量审计不得只抽样一个页面。

### 5.4 UI 完成定义

- 覆盖台账中的所有可达 route/deep-link × 4 视口均有本轮运行证据。
- 所有关键可写页面至少覆盖正常、空、错误、长内容和弹窗；高风险页面覆盖相应角色与无权限态。
- P0/P1 finding 为 0；P2 要么修复，要么在发布说明中有明确定位、负责人和不阻断理由。
- 全站综合 UI、UI consistency、button coverage、route browser、相关业务 verify 脚本均来自同一 HEAD 和同一 fixture 版本。
- 截图用于人工抽查和回归留证；验收以按钮功能、设计 token、布局几何、状态和可访问性断言为主，不以旧原型像素相似度作为完成标准。
