# HaoEMR 干净安装与模块初始化数据包实施计划

- 日期：2026-09-06
- 状态：规划已记录；运行时代码、数据包安装器和数据库改造尚未实施。
- 目标：用户部署后得到结构完整、可配置、无临床业务记录的系统，再按需安装模块配置；演示数据单独交付。
- 本次文档更新不执行数据库操作，不代表现有数据库已经清理或项目已经支持此安装方式。

## 1. 需要改什么

这是代码、交付文件和数据库演进共同参与的改造。项目文件包括代码、配置、迁移脚本、数据文件和文档；数据库变化应通过这些可版本管理的文件执行，不能只在某台机器上手工调整。

| 范围 | 现有位置与复用点 | 计划改动 |
|---|---|---|
| 数据导入后端 | `src/main/java/org/haoemr/development/SyntheticDataImporter.java` 及相关 importer | 分离必需底座、机构配置、模块配置和演示记录；正式初始化不调用开发导入器，不写死演示租户 UUID |
| 首次初始化 | `organization/`、`authorization/`、`security/` 现有领域服务 | 增加受控的首次租户/机构/管理员引导和初始化状态查询；解决现有管理接口先要求管理员身份的启动依赖 |
| 数据包安装 | `platform/CapabilityPackService.java`、`CapabilityPackReleaseService.java`、字典及模板领域服务 | 先评估已有能力包模型；扩展包预检、依赖解析、数据导入、安装证据和版本冲突处理，不另造重复业务内核 |
| 接口契约 | `contracts/openapi.json` 及生成流程 | 先定义初始化状态、包预检、安装结果和冲突等契约，再生成 Java/TypeScript 产物，不手改生成文件 |
| 用户页面 | `web/src/vue/`；已有机构、字典、能力包页面 | 增加首次设置和包安装流程；区分未配置、无业务数据、导入中、失败、就绪状态；移除生产流程对演示身份的依赖 |
| 数据包文件 | `samples/data/`、资源文件及迁移中的配置来源 | 计划新增 `data-packs/` 目录存放正式配置包，演示数据保留独立目录；先做病历模板包，再扩展模块 |
| 配置与部署 | `application*.yml`、`ProductionEnvironmentPostProcessor.java`、`deploy/`、`scripts/` | 分开干净安装与演示部署入口；提供正式构建和包清单；明确首次引导与正常运行的配置要求 |
| 数据库 | `src/main/resources/db/migration/` | 保留表、索引、约束、触发器与历史；盘点数据写入；按已审定方案补充初始化/安装状态、唯一性和来源追踪，优先复用已有表 |
| 验收与文档 | Java/Web 测试、`scripts/verify.sh`、CI、README 和部署说明 | 新增独立空库安装验收，保留演示回归；交付功能后记录真实命令、版本兼容与恢复步骤 |

上表的新目录、接口和状态机制均为计划项，不是现有可调用能力。

## 2. 数据分类与交付边界

| 类型 | 示例 | 初始化责任 |
|---|---|---|
| 结构与约束 | 表、索引、状态约束、不可变审计触发器、迁移历史 | 安装/升级自动执行，不由模块配置包改写 |
| 系统必需数据 | 运行必需的代码表、权限定义、内置协议或工具类型定义 | 随核心版本提供；清单逐项审核，不能把全部字典或全部 Agent 内容都视为必需 |
| 医院自身主数据 | 租户、机构、院区、科室、人员、管理员身份绑定 | 部署方通过引导或受控导入创建；不随通用数据包附赠医院和账号 |
| 可选模块配置 | 病历模板、可配置质控规则、护理项目、专科配置、Agent 内容配置 | 按需安装；规则和模板通过相关领域的审核/发布机制后生效 |
| 演示业务数据 | 虚构患者、就诊、医嘱、结果、模拟运行和评估记录 | 单独演示包，仅用于隔离开发/演示环境 |
| 外部连接及秘密 | 模型连接、OIDC、存储、CA、API 密钥 | 部署方配置；通用包只提供必要的参数说明，不包含账号口令和密钥 |

系统底座或模块配置安装完成后，患者、就诊、医嘱、收费和执行记录等业务表仍应为空；配置、审计和安装记录可以非空。导入医院真实历史数据属于独立迁移流程，不属于模块初始化。

结构迁移仍按统一内核执行；用户按需安装的是模块配置数据。首版不按用户所选模块动态删建数据库表，以免破坏跨模块依赖。

## 3. 当前已确认的工程事实

1. `application.yml` 启用 Flyway，迁移位置为 `classpath:db/migration`。
2. `SyntheticDataImporter` 使用 `@Profile("dev-synthetic")`，并在一次导入中创建机构、账号、配置和合成业务数据；`prod` 禁止合成环境并用。
3. 以行首 `INSERT INTO` 做初步文本扫描，29 个迁移文件命中。这个数字不代表 29 个演示脚本，也不是完整数据写入清单；其中可能有必要历史回填和系统配置，还需要检查 `UPDATE`、`DELETE`、函数、触发器及程序启动写入。
4. 现有能力包服务具备租户范围、继承检查、幂等键及审计/Outbox 写入；现有能力包定义/发布不等于通用数据文件安装器。
5. `ProductionEnvironmentPostProcessor` 在应用 Bean 和 Web 服务创建前校验 OIDC/MFA、证书、KMS、存储等生产配置。因而不能直接假设空配置部署后能够打开初始化网页。

## 4. 数据库怎么处理

### 全新安装

- 使用独立的新数据库验证，不复用演示库冒充空库。
- 运行经过分类验证的结构和必需底座迁移，再完成部署方机构及管理员引导。
- 保留数据库硬约束，不通过禁用触发器或外键导入模块包。
- 模块包将稳定业务编码映射为目标租户内的 ID，不复制演示租户外键。

### 已有实例升级

- 保留原数据库及 Flyway 历史，不自动清库、不修改已应用脚本的校验和。
- 保留医院现有配置及业务记录；已有配置只有核实来源后才能关联包版本，不能自动标记为“官方包原始内容”。
- 将新装和升级路径的最终结构进行比较，并测试升级后的历史记录和约束仍有效。

### 历史迁移夹带数据的处理决策

先在隔离空库执行现有迁移，确认哪些写入实际产生演示或可选数据，不能仅凭文件名删除脚本。

- 如果历史迁移只做结构、必要回填或对已有租户的补充，且新库不生成可选/演示记录，可继续保留迁移链；新租户的可选配置由安装器承担。
- 如果旧迁移会无条件污染新库，需设计并验证专用于全新安装的干净基线，以及旧库继续升级后汇合到同一结构的方案。具体基线版本和 Flyway 配置须在实现阶段验证，不能现在编造可执行命令。
- 已有数据库中若确实需要删除演示数据，另做来源识别、引用影响预览、备份和显式清理任务，不纳入默认升级脚本。

Flyway 会记录已执行迁移的校验和；已有版本的变更应优先通过后续迁移推进。参考：[Flyway versioned migrations](https://documentation.red-gate.com/fd/versioned-migrations-273973333.html)。

## 5. 首次初始化与数据包机制

### 首次入口

首版建议提供由部署管理员在部署环境执行的一次性引导，完成租户/机构创建、指定 OIDC 身份与管理员权限的绑定，并写入审计；随后进入认证后的配置页面。

引导需要验证操作来源，避免公网匿名抢占首个管理员；并发执行只能成功初始化一次，重复执行不得重置管理员。不能用关闭生产认证、开启开发身份或给全部用户临时管理员权限解决首次启动。

生产必需连接先按既有要求准备。若后续要求“未配置 CA/存储也能进入设置页”，应作为单独的受限设置模式设计，明确只允许设置相关操作，正常业务及后台任务在就绪前不可执行；不能静默放宽现有生产启动检查。

### 数据包格式与安装行为

- 包清单至少包含包编码、版本、类型、适用应用/结构版本、依赖、文件清单与哈希、来源和许可说明。哈希用于完整性校验；发布来源验证另行设计。
- 正式配置优先使用受约束的 JSON/CSV，经服务端字段校验和领域用例写入；首版不接受可执行代码或任意 SQL 包。
- 预检展示将新增、保留、更新及冲突的内容；缺依赖、错误版本、租户不匹配和文件损坏在写入前失败。
- 幂等键用于请求重试；另以租户、包版本及条目业务编码约束重复安装，不能只依赖短期幂等记录。
- 记录每个条目的安装来源、原始版本或哈希，才能识别医院修改。默认保留医院修改，更新冲突交给管理员处理。
- 安装完成和业务启用分开，复用已有审批、发布、权限及审计/Outbox 规则。导入不自动触发外部通知或模型调用。
- 首个小包在事务中写入；失败回滚业务写入并独立保留失败记录。未来大包需要明确批次、断点与恢复语义，不能宣称跨外部服务全局回滚。
- 包被业务引用后不能通过卸载删除历史记录；可停用未来使用，恢复旧配置必须遵守领域版本规则。

## 6. 下一步实施顺序与退出条件

| 阶段 | 交付物 | 完成标准 |
|---|---|---|
| P0 数据盘点与隔离基线 | 数据来源/目标表/类别/租户范围/依赖清单；空库迁移实测报告；新装与升级决策 | 每类初始数据都有责任归属；确认现有代码对空数据的假设；无现有库清理 |
| P1 最小安装设计与契约 | 初始化状态、受控引导、包格式、API 和页面流程；已有表复用说明 | 明确首个管理员如何建立、生产配置如何准备、重复执行如何处理 |
| P2 一个模块完整交付 | 最小系统初始化、病历模板包、安装页面与服务端导入、空状态工作台 | 从新数据库完成机构/管理员设置、安装模板；患者/就诊等业务记录为零；重复安装不重复建记录 |
| P3 演示与正式交付拆分 | 独立演示数据包、干净/演示部署入口、构建及 CI 检查 | 干净模式不创建合成账号、患者或模型运行结果；演示模式仍可完成原有业务演示 |
| P4 扩展和升级 | 护理、质控、专科及 AI 等模块包；依赖和版本升级流程 | 只安装所选包及明确依赖；医院修改不被静默覆盖；已有实例升级保留业务数据 |
| P5 文档与发布验收 | README 实际命令、部署说明、包兼容矩阵、失败恢复及升级操作说明 | 文档命令在全新环境实际跑通，规划状态按证据更新 |

P2 必须包含页面、API、数据库的完整链路，不能仅提交导入脚本或后端接口。P0 是下一步应执行的工程工作；本文件只完成方案记录，未将 P0 标为完成。

## 7. 必测场景

- 真正空库安装后，能建立管理员并进入设置；未初始化时无正常业务写入和后台自动执行。
- 完成初始化且不装模块包时，系统有清楚的空状态，不因缺少演示租户、患者或模板而报错。
- 安装模板包不创建患者/就诊；再次安装及并发安装不产生重复数据。
- 错误版本、损坏文件、缺失依赖、越权、跨租户引用在写入前拒绝。
- 中途失败可以重试；业务写入回滚或按已定义的批次恢复，安装记录准确。
- 医院改过模板后升级包，冲突可见、默认保留本地修改。
- 从旧版本数据库升级后，临床数据、权限、审计和 Flyway 历史保持有效。
- 正式构建不携带自动演示初始化入口；独立演示环境仍能运行原有回归。

## 8. README 更新纪律

README 现阶段只承诺目标和计划，不提供尚未实现的安装命令。每个阶段交付时同步更新当前状态、适用版本和已验证路径。P2/P3 完成后补充首次安装与两种部署方式；P4 完成后补充升级、冲突及恢复说明。历史测试结果不得用作本改造已经通过的证明。
