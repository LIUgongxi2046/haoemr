- 执行日期：2026-08-31（Asia/Shanghai）

- 分支：`main`
- 范围：PC Web（基线视口 1440×1000）、Java API、PostgreSQL 18.4、合成数据、AI Evals、低影响安全验证
- 明确排除：移动端不纳入本轮验收分母与发布门禁

## 1. 结论摘要

工程基线、合同、数据库、API、门诊主体页面、急诊、住院、质量中心及本地安全控制的大部分证据通过。三轮 PC 多角色链路均能稳定穿越门诊、急诊、住院、质控和系统管理域。

但严格发布门禁不能通过，原因是：

1. Java 全量回归 714 项中仍有 2 项稳定失败（业务配置导入期望与当前数据口径不一致）。
2. PC 预约挂号完整写链未跑通：班次选择控件不可见，班次号源配置页标题契约不匹配，入院页缺少验收要求的“入院途径”。
3. 全局 AI 医助对话输入框没有可访问名称，严格 UI 审计无法通过 `getByLabel`；AI 中心另有首个“编辑”按钮禁用导致的自动化契约失败。
4. 产品顶栏仅有临床医生、住院医生、质控管理员、系统管理员 4 个可切换角色；护士和药师无独立登录/角色入口，因而无法完成真实的职责分离用户验收。
5. DeepSeek 真实模型红队因模型制品、SHA-256、推理引擎、硬件和批准阈值未配置，门禁为 `INTEGRATED_BLOCKED`。

## 4. 多角色诊疗链路

使用当前产品实际存在的 4 个 PC 角色，连续执行 3 轮。每轮 26 个节点，共 78 个角色—页面节点，全部路由 ID、H1 与错误态检查通过。

1. 临床医生：预约挂号 → 门诊工作台 → 门诊病历 → 诊断 → 医嘱 → 检查检验 → 随访终诊。
2. 住院医生：急诊工作台 → 预检分诊 → 急诊病历 → 急诊护理 → 交接 → 入院床位 → 住院工作站 → 住院医嘱 → 病区护理 → 出院归档。
3. 质控管理员：全院病历 → 病历质控审签 → 医疗质量中心。
4. 系统管理员：系统管理 → 认证与账户安全策略。

这 3 轮证明的是 PC 角色上下文切换、跨域路由、数据展示和错误态稳定性。写入闭环由门诊、急诊、住院和质量中心的专项脚本提供。由于顶栏角色只是 4 个可见上下文，且没有护士/药师独立账号，本轮不把它表述为完整 RBAC/职责分离验收。

## 5. S010 安全工程与渗透结果

### 5.1 授权与方法

- 模式：`THREAT_MODEL + ASSESS + EXECUTE`
- 资产：合成患者数据、身份/角色、上下文租约、诊疗写入/签名、审计/Outbox、病案对象、AI 模型/工具副作用。
- 信任边界：浏览器↔会话/API、API↔PostgreSQL、API↔对象存储、API↔模型/工具、租户与患者/就诊上下文。
- 主要威胁：未授权/IDOR、伪造租户、SQL 注入、XSS、跨患者泄露、提示词注入、未授权工具副作用、证据篡改、秘密泄漏。
- 方法限制：只对本机合成环境进行低频、低影响请求；未做 DoS、密码爆破、数据外传、社会工程、生产/第三方测试。

## 6. 发布门禁与修复顺序

建议按以下顺序回到 S008 修复，然后定向重跑 S009/S010：

1. 修复预约挂号→报到→叫号→接诊→退号的 PC 完整写链，并核对班次配置和入院字段真值。
2. 为 AI 医助 composer 增加 label/`aria-label`，并让严格 UI 脚本按当前 Eva 交互契约执行。
3. 确定业务配置导入的最终数量口径，使 `TertiaryBusinessConfigurationImportTest` 零失败。
4. 修复全路由/按钮/一致性/顶栏/病历/病案/系统管理的自动化登录、选择器、前置数据和超时逻辑。
5. 增加护士与药师的独立测试账号/服务端角色任期，完成真实 RBAC 和职责分离链路。
6. 提供可校验的 DeepSeek 模型制品、硬件、推理引擎与批准阈值，再执行真实 AI 安全红队。

重跑通过条件：Java 全量零失败；PC 核心写链零 P0/P1；自动化工具无登录/契约误报；护士/药师角色链路可验证；真实模型安全门禁不再 `BLOCKED`。
